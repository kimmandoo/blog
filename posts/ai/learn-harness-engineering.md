# 1장

하네스는 기존의 "알아서 해줘" 방식에서 벗어나, 에이전트에게 환경, 상태, 검증, 제어 수단을 붙여주는 스캐폴딩 시스템이다. 모델 바깥에서 작업을 돕는 도구와 규칙은 대부분 하네스에 해당한다.

Codex든 Claude든, Opus든 Fable이든 모델과 상관없이 제공되는 엔지니어링 인프라가 하네스다.

하네스 없이 에이전트에게 무언가를 요구하면, 범위가 넓을수록 에이전트가 요구사항을 더 많이 추론해야 한다. 이 과정에서 의도와 다른 결과가 나올 가능성이 높아진다.

지시문이 명확하더라도 프로젝트 안에 숨어 있는 문맥까지 에이전트가 알 수는 없다. 특히 서면으로 남지 않은 정보라면 더 그렇다. 환경 문제는 최근 모델들이 꽤 잘 고치지만, 그 과정에서 토큰이 낭비된다. 검증도 마찬가지다. 에이전트가 컨텍스트 부족을 감지하면 세션을 어설프게 마무리하는 경우도 있다고 한다.

## Basic harness

원칙 1: 작업이 제대로 수행되지 않으면 하네스를 점검한다.

모델을 바꿔서 같은 작업을 시켰을 때 성공했다면, 모델보다 하네스를 먼저 다듬어야 한다.

크게 5단계로 접근한다.

1. 모든 실패를 특정 레이어에 묶어두기 - 각 실패를 작업 명세, 컨텍스트 제공, 실행 환경, 검증 피드백, 상태 관리 레이어 중 하나에 매핑해서 관리한다.
2. 모든 작업에 명시적인 완료 기준을 작성하기 - "해줘"로 끝내지 말고, 어떤 형식으로 어떤 기능을 만들지, 어떤 구현 방식을 쓸지, 검증은 어떻게 할지 정한다.

예시는 아래와 같다.

```text
완료 기준:
- 새 엔드포인트 GET /api/search?q=xxx
- 페이지네이션 지원, 기본 20개 항목
- 결과에 하이라이트된 스니펫 포함
- 모든 새 코드가 pytest 통과
- 타입 검사 통과 (mypy --strict)
```

3. AGENTS.md 파일 작성 - 저장소 루트에 작성해서 에이전트가 먼저 읽게 한다. 프로젝트 아키텍처, 코드에 없는 문맥, 기술 스택과 버전 같은 내용을 적어둘 수 있다.
4. 진단 루프 구축 - 실패가 반복될 때마다 실패한 레이어만 수정해서 하네스를 점점 강화한다.
5. 개선 사항 정량화 - 작업 단위마다 평가 기준을 만들고, 개선 전후를 비교한다.

# 2장

이미 유명한 모델들은 자체 하네스를 갖고 있다.

Claude Code는 `CLAUDE.md`를 읽고(레시피 선반), 셸 명령어를 실행할 수 있으며(칼 랙), 로컬 환경에서 실행되고(가스레인지), 세션 기록을 유지하며(준비 스테이션), 테스트를 실행하고 결과를 본다(품질 확인 창). 하지만 테스트 실행 방법을 알려주지 않으면 품질 확인 창이 없는 것과 같다. 요리가 제대로 익었는지 아무도 확인할 수 없다.

이 예시에서는 주방 비유가 꽤 잘 와닿았다.

Cursor도 비슷하다. `.cursorrules` 파일은 레시피 선반이고, 터미널은 칼 랙이며, 프로젝트 구조와 린트 설정을 읽는 능력은 가스레인지에 해당한다.

Codex는 git worktree를 사용해 각 작업의 런타임 환경을 격리하고, 로그, 메트릭, 트레이스와 결합해 변경 사항을 독립적인 환경에서 검증한다. AGENTS.md와 명확한 검증 명령어가 있는 저장소에서는 "맨손" 저장소보다 훨씬 안정적으로 동작한다.

Claude가 바보처럼 묘사된 것 같지만, 핵심은 따로 있다. 어떤 도구든 지시와 검증을 얼마나 구체적으로 제공하느냐가 결과를 크게 좌우한다.

## AGENTS.md

이 파일은 매뉴얼이 아니라 지도가 되어야 한다. 영문 기준 100줄 안팎을 권장하며, 규칙을 하나하나 길게 열거하지 않는 편이 좋다. 더 자세한 지시 사항은 docs로 분리해서 에이전트가 필요할 때 읽게 한다.

### 다시 주방으로 와서 5개 시스템으로 돌리기

1. 지시 하위 시스템(레시피 선반): AGENTS.md 또는 CLAUDE.md를 만들고 다음을 포함한다. 프로젝트 개요와 목적(한 문장), 기술 스택과 버전(Python 3.11, FastAPI 0.100+, PostgreSQL 15), 첫 실행 명령어(make setup, make test), 협상 불가능한 HARD 제약("모든 API는 OAuth 2.0을 사용해야 함"), 더 자세한 문서 링크.

2. 도구 하위 시스템(칼 랙): 에이전트가 충분한 도구 접근권을 갖게 한다. "보안"을 이유로 셸을 전부 막아두면 에이전트가 pip install조차 실행할 수 없다. 그렇다고 모든 권한을 열어두라는 뜻은 아니다. 최소 권한 원칙을 따른다.

3. 환경 하위 시스템(가스레인지): 환경 상태를 자기 설명적으로 만든다. 의존성 잠금에는 pyproject.toml 또는 package.json을 사용하고, 런타임 버전에는 .nvmrc 또는 .python-version을 둔다. 재현성이 중요하다면 Docker나 devcontainer를 사용한다.

4. 상태(state) 하위 시스템(준비 스테이션): 장시간 작업에는 진행 추적이 필요하다. 간단한 PROGRESS.md 파일에 완료된 것, 진행 중인 것, 차단된 것을 기록한다. 매 세션이 끝나기 전에 업데이트하고, 다음 세션을 시작할 때 읽는다.

5. 피드백 하위 시스템(품질 확인 창): 투자 대비 효과가 가장 큰 부분이다. AGENTS.md에 검증 명령어를 명시적으로 나열한다.

```text
검증 명령어:
- 테스트: pytest tests/ -x
- 타입 검사: mypy src/ --strict
- 린트: ruff check src/
- 전체 검증: make check (위 모두 포함)
```

모델을 바꿔가며 어떤 컴포넌트의 영향이 가장 큰지 파악하라는 내용도 있었지만, 대다수의 경우에는 모델을 하나만 사용할 것 같아서 이 부분은 넘어가도 될 듯하다.

# 3장

OpenAI는 저장소를 "시스템 오브 레코드(SoR, System of Record)"로 취급한다. 작업에 필요한 모든 컨텍스트가 구조화된 파일과 디렉터리 형태로 저장소 안에 있어야 한다는 뜻이다. 이걸 `repo as spec` 원칙이라고 부르는 것 같다.

요즘 에이전트는 웹 툴 호출도 꽤 잘하지만, 그래도 저장소 안에 기준 정보가 있는 편이 훨씬 안정적이다.

## 핵심 개념

지식 가시성 격차(Knowledge Visibility Gap): 전체 프로젝트 지식 중 저장소에 없는 지식의 비율. 격차가 클수록 에이전트의 실패율이 높아진다. 프로젝트에 대해 머릿속에만 있는 암묵지가 얼마나 되는지 생각해보고, 그중 얼마나 저장소에 들어갔는지 확인한다. 그 차이가 가시성 격차다.

시스템 오브 레코드(SoR, System of Record): 프로젝트 결정, 아키텍처 제약, 실행 상태, 검증 기준에 대한 권위 있는 출처로서의 코드 저장소. 저장소가 최종 발언권을 가지며, 다른 출처는 보조 자료가 된다. 도로 폐쇄가 지도에 표시되어 있으면 그 길로 가지 않는 것과 같다. 하지만 그 정보가 누군가의 머릿속에만 있다면 매번 그 사람에게 물어봐야 한다.

콜드 스타트 테스트(Cold-Start Test): 위의 다섯 가지 질문. 몇 개나 답할 수 있는지가 지도의 완성도를 보여준다.

발견 비용(Discovery Cost): 에이전트가 저장소에서 핵심 정보를 찾는 데 쓰는 컨텍스트 예산의 양. 정보가 숨어 있을수록 발견 비용이 높아지고, 실제 작업에 쓸 수 있는 예산은 줄어든다. 중요한 정보를 깊은 디렉터리 아래 README에 숨겨두면 존재하더라도 필요할 때 찾기 어렵다.

지식 부패율(Knowledge Decay Rate): 단위 시간당 낡아지는 지식 항목의 비율. 문서가 코드와 동기화되지 않는 것이 가장 큰 적이다. 낡은 문서는 문서가 없는 것보다 더 나쁠 수 있다.

ACID 유추: 데이터베이스 트랜잭션 원칙(원자성, 일관성, 격리성, 내구성)을 에이전트 상태 관리에 적용하는 것. 아래에서 자세히 설명한다.

## 지도 그리기

```text
project/
├── AGENTS.md              # 진입점: 프로젝트 개요, 실행 명령어, HARD 제약
├── src/
│   ├── api/
│   │   ├── ARCHITECTURE.md  # API 레이어 아키텍처 결정
│   │   └── ...
│   ├── db/
│   │   ├── CONSTRAINTS.md   # 데이터베이스 작업 HARD 제약
│   │   └── ...
│   └── ...
├── PROGRESS.md             # 현재 진행 상황: 완료, 진행 중, 차단됨
└── Makefile                # 표준화된 명령어: setup, test, lint, check
```

원칙 1: API 엔드포인트 인증에 관한 규칙은 거대한 전역 문서 안에 묻어두지 말고 API 코드 옆에 둔다. 각 모듈 디렉터리에 해당 모듈의 책임, 인터페이스, 특별 제약을 설명하는 짧은 문서를 둔다. 도서관 선반 라벨처럼.

원칙 2: 표준화된 진입 파일을 사용한다. AGENTS.md 또는 CLAUDE.md는 에이전트의 "랜딩 페이지"다. 모든 정보를 담을 필요는 없지만, 에이전트가 세 가지 질문에는 빠르게 답할 수 있어야 한다. "이 프로젝트가 무엇인가", "어떻게 실행하는가", "어떻게 검증하는가".

원칙 3: 모든 지식에는 명확한 사용 사례가 있어야 한다. 규칙을 제거해도 에이전트의 결정 품질에 영향이 없다면 그 규칙은 없어도 된다. 하지만 콜드 스타트 테스트의 모든 질문에는 답이 있어야 한다.

원칙 4: 모든 지식을 코드와 함께 업데이트한다. 아키텍처 문서를 해당 모듈 디렉터리에 두면, 코드를 수정할 때 자연스럽게 문서를 보게 된다. 코드 변경 후 CI에서 문서 업데이트가 필요한지 확인하도록 만들 수도 있다.

원칙4가 중요한게, codex로 일을 시킬 때 계속 예전 코드 기준으로 작성된 readme, testcode를 참조해서 잘못된 구현이 발생했던 적이 있다.

## ACID 원칙으로 에이전트 상태 관리하기

트랜잭션 원칙의 ACID는 에이전트 작업 상태에도 적용할 수 있다.

원자성(Atomicity): 각 작업은 하나의 git 커밋으로 묶고, 중간에 실패하면 git stash로 롤백한다. "반쯤 완료된" 상태를 남기지 않는다.

일관성(Consistency): "일관된 상태"의 검증 조건을 정의한다. 예를 들면 모든 테스트 통과, 린트 오류 없음 같은 조건이다. 에이전트는 각 작업 후 검증을 실행하고, 일관성 없는 중간 상태는 커밋하지 않는다.

격리성(Isolation): 여러 에이전트가 동시에 작업할 때 상태 파일에서 경쟁 조건이 생기지 않게 설계한다. 에이전트마다 자체 진행 파일을 쓰게 하거나, 격리를 위해 git 브랜치를 사용한다.

내구성(Durability): 중요한 프로젝트 지식은 git으로 추적되는 파일에 둔다. 임시 상태는 세션 메모리에 있어도 되지만, 세션 간에 이어져야 하는 지식은 파일에 영속화해야 한다.
