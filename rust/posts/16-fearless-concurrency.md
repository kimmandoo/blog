# 16. 겁 없는 동시성

동시성 장의 핵심은 "스레드를 많이 쓰는 법"이 아니라
데이터 경쟁 없이 일을 나누는 법입니다.
Rust는 `Send`/`Sync`와 소유권 규칙으로 위험한 패턴을 컴파일 단계에서 차단합니다.

## 핵심 개념과 원리

### 1) 스레드 생명주기

`thread::spawn`으로 작업을 분리하고,
`join`으로 종료를 기다리며 결과를 회수합니다.
작업이 끝나기 전에 메인 스레드가 종료되지 않도록 생명주기를 맞춰야 합니다.

### 2) 메시지 전달(channel) 우선

공유 상태보다 메시지 전달이 단순하고 안전합니다.
생산자-소비자 모델에서 `mpsc`는 실패 지점이 명확합니다.

### 3) 공유 상태가 필요하면 `Arc<Mutex<T>>`

멀티스레드 공유 소유는 `Arc`, 상호배제는 `Mutex`가 담당합니다.
락 범위를 짧게 유지해야 데드락과 성능 저하를 줄일 수 있습니다.

## 기술적인 심화 설명

### `move` 클로저와 소유권 이전

스레드 클로저는 보통 `move`를 사용합니다.
이때 캡처된 값 소유권이 스레드로 넘어가므로,
원본 스레드에서 계속 쓸 값은 `Arc::clone` 같은 전략이 필요합니다.

### `Send`/`Sync` 오토 트레잇 감각

- `Send`: 다른 스레드로 소유권 이전 가능
- `Sync`: 여러 스레드에서 참조 공유 가능

컴파일러 오류를 통해 "이 타입은 왜 스레드 안전하지 않은가"를 배울 수 있습니다.

## 대표 코드

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        tx.send("job done".to_string()).unwrap();
    });

    println!("{}", rx.recv().unwrap());
}
```

## 실습 문제 (3단계)

### 1) 기본

워커 스레드 3개를 생성해 각자 숫자를 채널로 보내고,
메인에서 합계를 계산하세요.

### 2) 응용

`Arc<Mutex<i32>>`로 공유 카운터를 만들고,
10개 스레드가 각각 100번 증가시키도록 구현하세요.

### 3) 도전

작업 큐를 채널로 만들고,
워커 풀 형태로 작업을 분배한 뒤 완료 로그를 수집하세요.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
use std::sync::mpsc;
use std::thread;

let (tx, rx) = mpsc::channel();
for n in 1..=3 {
    let tx = tx.clone();
    thread::spawn(move || tx.send(n).unwrap());
}
drop(tx);
let total: i32 = rx.iter().sum();
assert_eq!(total, 6);
```

### 응용 정답 예시

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];

for _ in 0..10 {
    let counter = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        for _ in 0..100 {
            *counter.lock().unwrap() += 1;
        }
    }));
}

for h in handles {
    h.join().unwrap();
}
```

### 도전 정답 방향

`mpsc::Sender<Job>`를 통해 작업을 던지고,
워커가 처리 후 결과 채널로 응답하는 2채널 구조를 사용합니다.

## 오답 예시 3종 + 해설

### 오답 1) `Rc<RefCell<T>>`를 멀티스레드에 사용

문제점: 스레드 안전하지 않아 컴파일 단계에서 거부됩니다.
개선: 멀티스레드 공유 상태는 `Arc<Mutex<T>>`로 전환하세요.

### 오답 2) 락을 너무 오래 잡기

문제점: 병렬성이 사라지고 데드락 위험이 커집니다.
개선: 필요한 최소 연산만 락 내부에서 수행하세요.

### 오답 3) 채널 sender를 drop하지 않음

문제점: receiver 루프가 종료 신호를 못 받아 무한 대기할 수 있습니다.
개선: 생산이 끝난 시점에 sender를 명시적으로 drop하세요.

## 미니 퀴즈 (정답 포함)

1) 멀티스레드 공유 상태 기본 조합이 `Arc<Mutex<T>>`인 이유는?
- 정답: `Arc`가 공유 소유를, `Mutex`가 상호배제를 제공해 데이터 경쟁을 막기 때문입니다.

2) 채널 기반 모델이 초보자에게 안전한 이유는?
- 정답: 공유 상태를 줄이고 메시지 흐름으로 실패 지점을 명확히 만들 수 있기 때문입니다.

3) sender를 drop하지 않으면 receiver에서 어떤 문제가 생길 수 있나요?
- 정답: 종료 신호를 받지 못해 수신 루프가 계속 대기할 수 있습니다.

## 부가 설명: 동시성에서 먼저 설계할 것은 데이터 흐름

스레드를 먼저 늘리기보다 데이터가 어떻게 이동하고 어디서 합쳐지는지를 먼저 그려 보세요.
메시지 전달 모델은 이 흐름을 명확히 표현하기 좋아서 초반 학습에 특히 유리합니다.

공유 상태가 필요한 경우에도 락 범위를 최소화해야 합니다.
락 내부에서 I/O나 오래 걸리는 계산을 수행하면 병렬성 이점이 거의 사라집니다.

## 아주 사소한 것까지: 용어 미니 사전

1. thread::spawn: 새 스레드를 생성합니다.
2. mpsc channel: 다중 생산자 단일 소비자 메시지 채널입니다.
3. Mutex<T>: 상호배제 락입니다.
4. join: 스레드 종료를 기다리고 결과를 회수합니다.
5. deadlock: 락 대기로 서로 영원히 진행하지 못하는 상태입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 메시지 전달

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 공유 상태 제어를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 락 범위 설계에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 종료 프로토콜를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
