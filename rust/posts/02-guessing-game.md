# 03. 첫 프로그램: 추리 게임 만들기

이 장은 02장에서 배운 변수/타입/제어흐름 기초를 실제 프로그램으로 연결하는 단계입니다.
이 장의 목표는 "작동하는 프로그램 하나 만들기"가 아닙니다.
입력, 파싱, 분기, 반복, 무작위 수 생성이라는 기본 요소를 연결해 Rust의 에러 처리 철학을 체감하는 것이 핵심입니다.

## 핵심 개념과 원리

### 1) 사용자 입력은 신뢰하지 않는 것이 기본

터미널 입력은 항상 문자열입니다.
따라서 숫자를 기대하더라도 바로 계산하지 않고, 먼저 정제(`trim`)와 변환(`parse`) 단계를 거쳐야 합니다.
이때 실패를 예외처럼 던지는 대신 `Result`로 다루는 것이 Rust 스타일입니다.

### 2) `match`는 분기 + 언패킹 + 문서화 역할을 동시에 한다

`match guess.cmp(&secret_number)`는 단순 if-else가 아닙니다.
`Ordering::Less`, `Greater`, `Equal` 같은 상태를 타입으로 강제하므로,
"어떤 경우를 처리했는지"가 코드에 명확히 드러납니다.

### 3) 루프는 상태 전이 모델이다

추리 게임은 사실 작은 상태 머신입니다.

- 입력 받기
- 파싱 시도
- 비교 결과 출력
- 정답이면 종료, 아니면 반복

이 흐름을 명확히 분리해 두면, 나중에 웹 서버/네트워크 코드에서도 같은 사고법을 재사용할 수 있습니다.

## 기술적인 심화 설명

### 왜 `parse::<u32>()`가 중요한가?

Rust의 `parse`는 "대충 변환"하지 않습니다.
문자열이 숫자 형식이 아니면 즉시 실패를 알려 줍니다.
이 강한 실패 모델 덕분에 데이터 정합성 문제가 빨리 드러납니다.

Kotlin에서도 `toIntOrNull()` 패턴으로 비슷한 방어 코드를 짤 수 있지만,
Rust는 컴파일러가 `Result` 처리를 강제하기 때문에 누락이 덜 발생합니다.

### `rand` 크레이트를 쓸 때 배우는 것

외부 의존성 추가(`Cargo.toml`)는 단순 설치가 아닙니다.

- 어떤 버전을 쓰는지
- API가 바뀌면 어디가 깨질 수 있는지
- 잠금 파일(`Cargo.lock`)로 재현성이 유지되는지

Chapter 2는 이 의존성 생태계를 처음 경험하는 장입니다.

## 대표 코드

```rust
use rand::Rng;
use std::cmp::Ordering;
use std::io;

fn main() {
    let secret_number = rand::thread_rng().gen_range(1..=100);

    loop {
        let mut input = String::new();
        io::stdin().read_line(&mut input).expect("failed to read line");

        let guess: u32 = match input.trim().parse() {
            Ok(n) => n,
            Err(_) => {
                println!("숫자를 입력하세요.");
                continue;
            }
        };

        match guess.cmp(&secret_number) {
            Ordering::Less => println!("Too small!"),
            Ordering::Greater => println!("Too big!"),
            Ordering::Equal => {
                println!("You win!");
                break;
            }
        }
    }
}
```

## 실습 문제 (3단계)

### 1) 기본: 입력 검증 강화

현재 코드에 "1~100 범위 밖 숫자"를 거부하는 로직을 추가하세요.
범위를 벗어나면 비교하지 않고 다음 입력을 받도록 만드세요.

### 2) 응용: 시도 횟수 제한

최대 시도 횟수를 7회로 제한하고,
실패 시 정답을 출력한 뒤 종료하도록 확장하세요.

### 3) 도전: 재시작 가능한 게임

한 판이 끝나면 "다시 할까요?(y/n)"를 물어보고,
`y`면 새 정답 숫자를 생성해 게임을 다시 시작하세요.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
if !(1..=100).contains(&guess) {
    println!("1~100 사이 숫자만 입력하세요.");
    continue;
}
```

핵심 해설:

- 검증 실패를 정상 분기(`continue`)로 처리해 프로그램 안정성을 유지합니다.

### 응용 정답 예시

```rust
let mut attempts = 0u8;
let max_attempts = 7u8;

loop {
    attempts += 1;
    // ... 입력/파싱/비교 ...

    if attempts >= max_attempts {
        println!("실패! 정답은 {secret_number}였습니다.");
        break;
    }
}
```

핵심 해설:

- 상태(`attempts`)를 명시적으로 들고 가면 로직이 예측 가능해집니다.

### 도전 정답 예시

```rust
fn ask_restart() -> bool {
    let mut line = String::new();
    std::io::stdin().read_line(&mut line).expect("failed to read line");
    matches!(line.trim(), "y" | "Y")
}
```

구조화 방향:

- `play_one_round() -> bool`처럼 한 판 책임을 분리합니다.
- `main`은 반복 여부만 제어합니다.

## 오답 예시 3종 + 해설

### 오답 1) `parse().unwrap()` 남용

```rust
let guess: u32 = input.trim().parse().unwrap();
```

문제점: 숫자가 아닌 입력에서 즉시 패닉이 발생해 사용자 경험이 무너집니다.
개선: `match` 또는 `if let`로 오류를 처리하고 루프를 계속 유지합니다.

### 오답 2) 범위 검증 없이 바로 비교

문제점: `0`, `999` 같은 값도 게임 흐름으로 들어가 학습 목적이 흐려집니다.
개선: 도메인 규칙(1~100)을 코드로 명시하세요.

### 오답 3) 루프 종료 조건이 분산된 코드

문제점: 여러 곳에서 `break`를 남발하면 상태를 추적하기 어렵습니다.
개선: 종료 조건(정답, 횟수 초과, 재시작 거부)을 명확히 구분하고 함수로 분리하세요.

## 이 장에서 꼭 가져갈 습관

1. 파싱 실패는 예외가 아니라 정상 분기다.
2. 상태를 변수로 명확히 들고 다녀라.
3. 게임 로직을 함수로 쪼개 테스트 가능한 구조를 의식하라.

## 미니 퀴즈 (정답 포함)

1) 사용자 입력 파싱 실패에서 `unwrap()` 대신 `match`를 쓰는 이유는?
- 정답: 잘못된 입력을 정상 분기로 처리해 프로그램이 계속 동작하도록 만들기 위해서입니다.

2) 추리 게임에서 루프를 "상태 머신"으로 보는 관점의 장점은?
- 정답: 종료 조건, 전이 조건, 반복 조건을 분리해 로직 추적과 확장이 쉬워집니다.

3) 범위 검증(1~100)을 비교 전에 두는 이유는?
- 정답: 도메인 규칙을 먼저 보장해 잘못된 입력이 핵심 비교 로직을 오염시키지 않도록 하기 위해서입니다.

## 학습 완료 기준

1. 입력 파싱 실패를 panic 없이 처리한다.
2. 상태(시도 횟수/종료 조건)를 명시 변수로 관리한다.
3. 재시작 가능한 게임 루프를 함수로 분리한다.

## 실전 확장 미션

1. 난이도(숫자 범위) 선택 기능 추가
2. 최고 기록(최소 시도 횟수) 저장 기능 구현

## 부가 설명: 입력 중심 프로그램에서 사고하는 방법

이 장의 핵심은 게임이 아니라 "신뢰할 수 없는 입력"을 다루는 태도입니다.
터미널 입력은 항상 실패할 수 있다는 전제를 두면, 이후 파일/네트워크/API 입력에도 같은 패턴을 재사용할 수 있습니다.

특히 `continue`를 통해 실패를 정상 흐름으로 되돌리는 패턴은 매우 중요합니다.
프로그램을 멈추는 대신 복구 경로를 설계하는 습관이 실무 코드 안정성을 크게 높여 줍니다.

## 아주 사소한 것까지: 용어 미니 사전

1. parse: 문자열을 다른 타입으로 변환합니다.
2. Result<T, E>: 성공(T)/실패(E)를 표현하는 타입입니다.
3. match: 가능한 경우를 빠짐없이 처리하는 분기 문법입니다.
4. continue: 현재 반복을 건너뛰고 다음 반복으로 진행합니다.
5. state machine: 상태 전이 규칙으로 로직을 보는 모델입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 입력 검증

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 루프 상태 관리를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 파싱 실패 복구에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: CLI 사용자 경험를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
