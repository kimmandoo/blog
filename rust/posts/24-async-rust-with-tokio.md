# 24. Async Rust와 Tokio 입문

이 장은 동기 코드 중심 학습에서 비동기 생태계로 넘어가는 다리 역할을 합니다.
"왜 async가 필요한지", "언제 thread와 구분해야 하는지"를 실전 관점에서 설명합니다.

## 핵심 개념과 원리

### 1) async는 병렬이 아니라 비동기 대기 관리다

`async/await`는 CPU 작업을 자동 병렬화하지 않습니다.
I/O 대기 시간을 효율적으로 처리하는 모델입니다.

### 2) Runtime이 실행을 담당한다

Rust async 함수는 스스로 실행되지 않고 Future를 반환합니다.
Tokio 같은 runtime이 이를 poll해서 실제 진행시킵니다.

### 3) task와 thread를 구분해야 한다

task는 경량 실행 단위, thread는 OS 스레드입니다.
문제 유형에 따라 선택 기준이 달라집니다.

## 기술적인 심화 설명

### `Send`와 `!Send` Future

멀티스레드 런타임에서 task 이동 가능성 때문에 `Send` 제약이 중요합니다.
`Rc<RefCell<_>>` 같은 타입은 async 경계에서 종종 문제를 만듭니다.

### blocking 코드 혼합 주의

비동기 컨텍스트에서 오래 걸리는 동기 작업을 직접 실행하면 런타임 정체가 발생합니다.
`spawn_blocking`으로 격리하는 패턴을 익혀야 합니다.

## 대표 코드

```rust
use tokio::time::{sleep, Duration};

async fn fetch_profile(user_id: u64) -> String {
    sleep(Duration::from_millis(200)).await;
    format!("user-{user_id}")
}

#[tokio::main]
async fn main() {
    let a = tokio::spawn(fetch_profile(1));
    let b = tokio::spawn(fetch_profile(2));

    let (ra, rb) = tokio::join!(a, b);
    println!("{:?} {:?}", ra.unwrap(), rb.unwrap());
}
```

## 실습 문제 (3단계)

### 1) 기본

비동기 함수 2개를 만들어 `join!`으로 동시에 실행하세요.

### 2) 응용

실패 가능 함수를 `Result`로 반환하고 `try_join!`으로 합치세요.

### 3) 도전

동기 파일 읽기 코드를 `spawn_blocking`으로 분리해 런타임 정체를 피하세요.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
let (a, b) = tokio::join!(async_task_a(), async_task_b());
println!("{a} {b}");
```

### 응용 정답 예시

```rust
let (a, b) = tokio::try_join!(fetch_a(), fetch_b())?;
```

### 도전 정답 방향

CPU/동기 I/O가 길면 `tokio::task::spawn_blocking`으로 분리해 event loop 점유를 줄입니다.

## 오답 예시 3종 + 해설

### 오답 1) async 함수 호출만 하고 `.await` 누락

문제점: Future만 만들고 실행하지 않아 기대 동작이 일어나지 않습니다.
개선: 호출 지점에서 await 또는 spawn/join으로 실행을 트리거하세요.

### 오답 2) 비동기 안에서 긴 동기 작업 직접 실행

문제점: 런타임 스레드가 막혀 전체 처리량이 급감합니다.
개선: blocking 구간은 별도 경로로 격리하세요.

### 오답 3) thread와 task 개념 혼동

문제점: 불필요한 스레드 생성/동기화 비용이 늘어납니다.
개선: I/O 동시성은 task, CPU 병렬은 thread 중심으로 설계하세요.

## 이 장에서 꼭 가져갈 습관

1. 비동기와 병렬을 구분해 생각한다.
2. blocking 코드는 명시적으로 격리한다.
3. 실패 모델(Result)을 async 경계에서도 유지한다.

## 미니 퀴즈 (정답 포함)

1) async 함수는 호출 즉시 실행되나요?
- 정답: 아니요. Future를 반환하고 await/poll될 때 진행됩니다.

2) Tokio runtime이 필요한 이유는?
- 정답: Future를 스케줄링하고 poll해 실제 실행을 진행하기 위해서입니다.

3) 동기 블로킹 작업을 async 내부에서 그대로 실행하면 왜 문제인가요?
- 정답: event loop를 막아 다른 task 진행이 지연됩니다.

## 부가 설명: 왜 이 장이 실무 전환점인가

많은 Rust 프로젝트는 CLI로 시작해 네트워크/서버로 확장됩니다.
이때 async 모델을 제대로 이해하지 못하면 성능 문제를 감으로 해결하려다 더 복잡해집니다.

초반에 runtime, task, blocking 분리 감각을 잡아 두면 이후 웹 백엔드/마이크로서비스 학습이 훨씬 수월합니다.

## 아주 사소한 것까지: 용어 미니 사전

1. Future: 비동기 연산 상태를 담는 값입니다.
2. poll: Future 진행 상태를 확인/진행시키는 호출입니다.
3. runtime: Future를 스케줄링/실행하는 엔진입니다.
4. task: runtime이 관리하는 경량 실행 단위입니다.
5. backpressure: 처리량 한계를 넘는 입력을 제어하는 전략입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 비동기 실행 모델

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 런타임 이해를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: task/thread 구분에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: blocking 격리를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
