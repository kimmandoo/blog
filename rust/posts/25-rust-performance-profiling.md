# 25. Rust 성능 최적화와 프로파일링

이 장은 "빠르게 보이는 코드"가 아니라 "실제로 빨라진 코드"를 만드는 방법을 다룹니다.
핵심은 감이 아니라 측정입니다.

## 핵심 개념과 원리

### 1) 최적화 전 측정이 먼저

문제가 CPU인지, 메모리인지, I/O인지 모르면 올바른 최적화가 불가능합니다.
항상 baseline을 먼저 기록하세요.

### 2) 핫패스만 최적화

전체 코드가 아닌 실제로 시간이 많이 쓰이는 경로만 개선해야 효율이 높습니다.

### 3) 알고리즘 > 미세 튜닝

자료구조와 알고리즘 선택이 가장 큰 성능 차이를 만듭니다.
문법 수준 미세 최적화는 마지막 단계입니다.

## 기술적인 심화 설명

### 벤치마크 신뢰도

캐시 워밍, 입력 크기, 릴리스 빌드 여부에 따라 수치가 크게 바뀝니다.
측정 환경을 고정하고 여러 번 반복해 분산을 확인해야 합니다.

### 할당 줄이기 전략

불필요한 `String` 생성, 중간 `Vec` 할당, clone 남용이 대표 병목입니다.
borrow 기반 API, iterator 연결, pre-allocation을 활용하세요.

## 대표 코드

```rust
fn count_words_naive(text: &str) -> usize {
    text.split_whitespace().map(|w| w.to_string()).count()
}

fn count_words_fast(text: &str) -> usize {
    text.split_whitespace().count()
}
```

## 실습 문제 (3단계)

### 1) 기본

동일 입력으로 naive/fast 버전을 각각 1000회 실행해 시간 차이를 기록하세요.

### 2) 응용

`HashMap` 기반 집계 함수에서 clone 횟수를 줄이는 리팩터링을 하세요.

### 3) 도전

프로파일링 결과를 기준으로 상위 2개 병목만 개선하고, 개선 전후 수치를 표로 정리하세요.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
let start = std::time::Instant::now();
for _ in 0..1000 {
    let _ = count_words_fast(text);
}
println!("elapsed={:?}", start.elapsed());
```

### 응용 정답 방향

키 문자열을 매번 새로 만들지 말고, 가능하면 참조 기반 처리 후 최종 단계에서만 소유화하세요.

### 도전 정답 핵심

개선 수치(예: p50/p95, 메모리 사용량)를 함께 기록해야 최적화의 신뢰도가 올라갑니다.

## 오답 예시 3종 + 해설

### 오답 1) 측정 없이 최적화

문제점: 시간은 썼지만 성능 개선이 거의 없을 수 있습니다.
개선: baseline과 목표 수치를 먼저 정의하세요.

### 오답 2) 릴리스 빌드 없이 성능 판단

문제점: dev 빌드 수치는 실전 성능을 대표하지 못합니다.
개선: 성능 평가는 `--release` 기준으로 하세요.

### 오답 3) 코드 가독성 파괴

문제점: 미세 최적화로 유지보수성이 떨어지면 장기 비용이 증가합니다.
개선: 성능 이득이 명확한 구간만 최소 범위로 최적화하세요.

## 이 장에서 꼭 가져갈 습관

1. 먼저 측정, 나중 최적화.
2. 병목 상위 구간만 집중 개선.
3. 수치와 근거를 남기는 최적화 문화 유지.

## 미니 퀴즈 (정답 포함)

1) "빠를 것 같은 코드"와 "빠른 코드"의 차이는?
- 정답: 측정 수치로 검증되었는지 여부입니다.

2) 왜 알고리즘 개선이 미세 최적화보다 중요한가요?
- 정답: 복잡도 차이가 입력 크기 증가 시 성능 격차를 크게 만들기 때문입니다.

3) 프로파일링 없이 최적화하면 흔한 결과는?
- 정답: 핫패스가 아닌 구간만 개선해 체감 성능이 거의 변하지 않습니다.

## 학습 완료 기준

1. baseline 측정 루프를 직접 구성한다.
2. 병목 지점을 근거 기반으로 설명한다.
3. 개선 전후 수치를 비교해 최적화 효과를 입증한다.

## 실전 확장 미션

1. 실제 프로젝트 함수 1개를 선택해 성능 개선 리포트 작성
2. 팀 공용 "최적화 체크리스트" 문서 작성

## 부가 설명: 고급 숙련자에게 필요한 관점

고급 개발자는 "빠른 코드"보다 "지속 가능한 빠른 코드"를 만듭니다.
즉, 성능/가독성/안전성의 균형점을 찾는 능력이 중요합니다.

측정 기반 개선 습관이 자리 잡으면, 대규모 서비스에서도 최적화가 개인 기술이 아니라 팀 프로세스로 정착됩니다.

## 아주 사소한 것까지: 용어 미니 사전

1. baseline: 개선 전 기준 성능 수치입니다.
2. hot path: 실행 시간 대부분이 집중되는 코드 경로입니다.
3. throughput: 단위 시간당 처리량입니다.
4. latency: 요청 하나가 끝나는 데 걸리는 시간입니다.
5. profiling: 실행 중 성능 병목을 측정/분석하는 과정입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 측정 기반 최적화

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 핫패스 분석를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 할당 최소화에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 성능 보고 문화를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
