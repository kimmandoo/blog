# 18. 패턴 매칭 고급 문법

Chapter 18은 패턴 매칭을 "분기 문법"이 아니라 "데이터 해체 도구"로 쓰는 장입니다.
복잡한 if-else를 패턴으로 바꾸면 의도와 누락 여부가 훨씬 명확해집니다.

## 핵심 개념과 원리

### 1) 구조 분해 패턴

튜플, 구조체, enum을 한 번에 해체해 필요한 값만 꺼낼 수 있습니다.

### 2) 패턴 가드 (`if`)

패턴 자체와 추가 조건을 함께 기술해 분기 의도를 선명하게 표현합니다.

### 3) `@` 바인딩

범위 매칭과 값 바인딩을 동시에 수행할 수 있어 로그/검증 코드가 깔끔해집니다.

## 기술적인 심화 설명

### `_`와 `..`를 언제 써야 하나

필요 없는 필드를 명시적으로 무시하면 코드 노이즈가 줄어듭니다.
단, 핵심 분기에서 과도한 `_`는 누락을 숨길 수 있으니 주의해야 합니다.

### `if let` 체인 vs `match`

한 케이스만 중요하면 `if let`,
여러 케이스가 동등하게 중요하면 `match`가 읽기 쉽습니다.

## 대표 코드

```rust
enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
}

fn handle(msg: Message) {
    match msg {
        Message::Quit => println!("quit"),
        Message::Move { x, y: 0 } => println!("move on x-axis: {x}"),
        Message::Move { x, y } if x == y => println!("diagonal: {x}, {y}"),
        Message::Move { x, y } => println!("move: {x}, {y}"),
        Message::Write(text) => println!("text: {text}"),
    }
}
```

## 실습 문제 (3단계)

### 1) 기본

`enum Event { Login(String), Logout, Error(u16) }`를 패턴 매칭으로 처리.

### 2) 응용

중첩 튜플 `(Option<i32>, Result<&str, &str>)`를 패턴으로 해체해 로그 출력.

### 3) 도전

`@` 바인딩을 사용해 `id @ 100..=199` 구간을 별도 처리.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
fn event_label(event: Event) -> String {
    match event {
        Event::Login(name) => format!("login:{name}"),
        Event::Logout => "logout".to_string(),
        Event::Error(code) => format!("error:{code}"),
    }
}
```

### 응용 정답 방향

`match (opt, res)` 형태로 4개 케이스를 완전하게 다뤄 분기 누락을 없앱니다.

### 도전 정답 예시

```rust
match id {
    vip @ 100..=199 => println!("vip id: {vip}"),
    _ => println!("normal id"),
}
```

## 오답 예시 3종 + 해설

### 오답 1) 중첩 if-else로 모든 경우 처리

문제점: 누락 케이스를 발견하기 어렵습니다.
개선: 패턴 매칭으로 케이스를 타입 기반으로 열거하세요.

### 오답 2) `_`로 대부분 케이스 뭉개기

문제점: 새 variant 추가 시 버그가 숨어버립니다.
개선: 핵심 도메인 분기는 가능한 명시적으로 매칭하세요.

### 오답 3) 가드 조건을 arm 밖에서 중복 검사

문제점: 분기 로직이 분산돼 읽기 어려워집니다.
개선: `match` arm의 guard로 조건을 통합하세요.

## 미니 퀴즈 (정답 포함)

1) 패턴 가드(`if`)를 `match` arm에 붙이는 장점은?
- 정답: 패턴과 조건을 한 곳에 묶어 분기 의도를 명확하게 표현할 수 있습니다.

2) `_` 패턴을 과도하게 쓰면 왜 위험한가요?
- 정답: 신규 케이스 누락이 숨어 리팩터링 안정성이 떨어집니다.

3) `@` 바인딩은 언제 유용한가요?
- 정답: 범위/형태를 매칭하면서 동시에 원본 값을 이름으로 재사용하고 싶을 때 유용합니다.

## 학습 완료 기준

1. 중첩 데이터를 패턴으로 해체한다.
2. guard와 `@` 바인딩을 적절히 활용한다.
3. 핵심 분기에서 `_` 남용을 피한다.

## 실전 확장 미션

1. 로그 이벤트 분류기 구현
2. 패턴 리팩터링 전후 분기 수 비교

## 부가 설명: 패턴은 분기를 줄이는 문법이 아니라 모델 해체 도구

if-else를 match로 바꿀 때 중요한 것은 줄 수가 아니라 의미의 선명도입니다.
패턴만 보고도 어떤 데이터 형태를 기대하는지 읽히면 유지보수성이 크게 향상됩니다.

`_`와 가드를 적절히 쓰는 균형도 중요합니다.
핵심 도메인 분기에서는 명시 매칭을 유지하고, 보조 분기에서만 축약 패턴을 쓰는 습관이 좋습니다.

## 아주 사소한 것까지: 용어 미니 사전

1. destructuring: 복합 데이터를 패턴으로 해체합니다.
2. match guard: 패턴 매칭 arm에 추가 조건을 붙입니다.
3. @ binding: 매칭과 바인딩을 동시에 수행합니다.
4. wildcard (_): 필요 없는 값 매칭 축약 기호입니다.
5. if let: 단일/소수 케이스를 간단히 다루는 문법입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 데이터 해체

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 패턴 가드를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 분기 명시성에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 도메인 규칙 반영를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
