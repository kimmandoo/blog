# 23. 초중급을 잇는 Rust 문법 레시피

이 장은 Rust Book 완주 후에도 계속 헷갈리는 기초 문법을 빠르게 다시 꺼내 보는 복습 장입니다.
초보자는 "왜 이 코드가 안 되는지"를 찾는 시간을 줄이고, 중급자는 실수 패턴을 빠르게 교정하는 데 목적이 있습니다.

## 핵심 개념과 원리

### 1) 타입은 문법이 아니라 계약이다

`u32`와 `i32` 차이는 부호 유무를 넘어 입력 검증 전략까지 바꿉니다.
타입 선택은 "값의 의미"를 결정하는 설계 행위입니다.

### 2) 표준 패턴을 외우면 디버깅 시간이 줄어든다

`Option` 언패킹, `Result` 전파, `match` 완전성, `iter` 체인 같은 패턴은 반복됩니다.
자주 쓰는 형태를 레시피로 기억해 두면 코드를 빠르게 안정화할 수 있습니다.

### 3) 기초 문법 오류는 대부분 경계에서 발생한다

문자열 파싱, 인덱스 접근, 형변환, 소유권 이동 같은 경계 지점이 실제 오류의 대부분입니다.
경계 지점 먼저 방어하는 습관이 중요합니다.

## 기술적인 심화 설명

### "컴파일은 되는데 이상한 코드"를 거르는 기준

컴파일 성공은 최소 조건일 뿐입니다.
읽기 어렵고 의미가 모호한 코드는 장기적으로 더 큰 장애를 만듭니다.

### 레시피 기반 학습의 장점

한 번에 이론을 완벽히 이해하려고 하면 속도가 느려집니다.
자주 쓰는 문제-해결 쌍(레시피)을 먼저 체득하고, 필요할 때 원리로 확장하는 방식이 효율적입니다.

## 대표 코드

```rust
fn parse_non_empty_u32(input: &str) -> Result<u32, String> {
    let trimmed = input.trim();
    if trimmed.is_empty() {
        return Err("input is empty".to_string());
    }

    trimmed
        .parse::<u32>()
        .map_err(|_| "input is not a valid u32".to_string())
}
```

## 실습 문제 (3단계)

### 1) 기본

위 함수를 확장해 `0`을 허용하지 않는 버전을 작성하세요.

### 2) 응용

입력 리스트(`Vec<&str>`)를 받아 유효한 값만 `Vec<u32>`로 모으고, 실패 개수를 함께 반환하세요.

### 3) 도전

에러를 문자열 대신 enum으로 분리하고 `Display`를 구현하세요.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
fn parse_non_zero_u32(input: &str) -> Result<u32, String> {
    let value = parse_non_empty_u32(input)?;
    if value == 0 {
        return Err("value must be greater than 0".to_string());
    }
    Ok(value)
}
```

### 응용 정답 예시

```rust
fn collect_valid(inputs: &[&str]) -> (Vec<u32>, usize) {
    let mut out = Vec::new();
    let mut failures = 0;

    for s in inputs {
        match parse_non_empty_u32(s) {
            Ok(v) => out.push(v),
            Err(_) => failures += 1,
        }
    }

    (out, failures)
}
```

### 도전 정답 방향

`enum ParseError { Empty, NotNumber, ZeroNotAllowed }`로 분리하면 상위 계층에서 실패별 대응이 가능합니다.

## 오답 예시 3종 + 해설

### 오답 1) `unwrap()` 연쇄

문제점: 입력 오류를 패닉으로 바꿔 복구 경로가 사라집니다.
개선: `Result`를 유지하고 상위에서 분기하세요.

### 오답 2) 타입 추론에만 의존

문제점: 읽는 사람 입장에서 의도가 불명확해집니다.
개선: 경계 함수 시그니처는 명시 타입을 사용하세요.

### 오답 3) 경계 조건 생략

문제점: 빈 문자열/0/공백 입력이 실제 장애로 이어집니다.
개선: 경계 검증을 함수 초반에 배치하세요.

## 이 장에서 꼭 가져갈 습관

1. 경계 입력을 먼저 방어한다.
2. 실패 경로를 타입으로 분리한다.
3. 자주 쓰는 패턴을 레시피로 축적한다.

## 미니 퀴즈 (정답 포함)

1) `Result`를 문자열 에러 하나로 뭉개면 무엇이 손해인가요?
- 정답: 실패 원인별 복구 전략을 선택하기 어려워집니다.

2) 기초 문법 복습이 고급 주제에 왜 중요한가요?
- 정답: 고급 코드는 결국 기본 문법/타입 조합으로 구성되기 때문입니다.

3) 경계 입력 검증을 함수 초반에 두는 이유는?
- 정답: 이후 로직을 단순화하고 오류 전파를 일관화할 수 있기 때문입니다.

## 학습 완료 기준

2. `Option`/`Result`를 상황에 맞게 구분해 사용한다.
3. 자주 틀리는 기초 문법 오류를 스스로 교정한다.

## 부가 설명: 초중급 사이에서 가장 많이 흔들리는 순간

많은 학습자가 "기초는 안다"고 생각한 뒤 곧바로 고급 주제로 넘어갑니다.
하지만 실제로는 경계 입력, 에러 모델, 타입 의도 표현 같은 기초가 약해서 다시 막히는 경우가 많습니다.

이 장은 그 틈을 메우기 위한 안전장치입니다.
빠르게 다시 보고 바로 적용할 수 있게 짧은 레시피 단위로 구성했습니다.

## 아주 사소한 것까지: 용어 미니 사전

1. parsing: 문자열을 특정 타입 값으로 변환하는 과정입니다.
2. boundary input: 비정상/경계에 걸친 입력 값입니다.
3. fallback: 실패 시 대체 동작 경로입니다.
4. recipe: 반복되는 문제의 표준 해결 패턴입니다.
5. invariant: 항상 유지해야 하는 상태 규칙입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 기초 레시피

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 실수 교정를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 입력 경계에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 문법 회복력를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
