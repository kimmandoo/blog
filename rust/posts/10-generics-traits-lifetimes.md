# 10. 제네릭, 트레잇, 라이프타임

이 장은 Rust 추상화의 핵심입니다.
제네릭은 중복을 줄이고, 트레잇은 능력을 명시하며, 라이프타임은 참조 유효성을 증명합니다.
셋을 함께 이해하면 "유연한데 안전한 API"를 만들 수 있습니다.

## 핵심 개념과 원리

### 1) 제네릭: 데이터 타입이 바뀌어도 로직은 유지

```rust
fn largest<T: PartialOrd + Copy>(list: &[T]) -> T {
    let mut largest = list[0];
    for &item in list.iter() {
        if item > largest {
            largest = item;
        }
    }
    largest
}
```

핵심은 "아무 타입이나"가 아니라
"필요한 능력(비교, 복사)을 가진 타입만" 허용하는 데 있습니다.

### 2) 트레잇: 타입의 행동 계약

트레잇은 인터페이스 그 이상입니다.
어떤 타입이 시스템에 참여하기 위한 최소 능력을 선언합니다.

```rust
trait Summary {
    fn summary(&self) -> String;
}
```

### 3) 라이프타임: 참조 관계를 타입으로 표현

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}
```

`'a`는 "두 입력 참조와 반환 참조의 생존 관계"를 알려 줍니다.
메모리를 늘리는 개념이 아니라 관계 표기입니다.

## 기술적인 심화 설명

### 트레잇 바운드는 최소한으로

불필요하게 `Clone + Debug + Display + ...`를 붙이면 API 재사용성이 떨어집니다.
정말 필요한 능력만 요구해야 호출자 부담이 줄어듭니다.

### `impl Trait` vs 제네릭 타입 파라미터

- 단일 인자/반환에서 단순 표현: `impl Trait`
- 여러 타입 관계를 묶어야 할 때: `T: Trait`

설계 의도가 더 잘 드러나는 쪽을 선택하면 됩니다.

### Kotlin 제네릭과 비교

Kotlin도 상한 제한(`where T : Comparable<T>`)이 있지만,
Rust는 소유권/수명까지 타입 시스템에 걸려 있기 때문에
추상화 설계가 메모리 안전성과 직접 연결됩니다.

## 대표 코드

```rust
trait Render {
    fn render(&self) -> String;
}

fn print_preview<T: Render>(item: &T) {
    println!("{}", item.render());
}

fn pick_longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() > b.len() { a } else { b }
}
```

## 실습 문제 (3단계)

### 1) 기본: 제네릭 최대값 함수

`i32`, `char` 배열 모두에 동작하는 `largest` 함수를 작성하세요.
필요한 trait bound를 스스로 결정하세요.

### 2) 응용: 트레잇 기반 알림 시스템

`trait Notifiable { fn message(&self) -> String }`를 만들고,
`Email`, `Slack` 타입이 이를 구현하도록 작성하세요.

### 3) 도전: 라이프타임 포함 파서

입력 문자열에서 첫 토큰을 반환하는 함수
`fn first_token<'a>(line: &'a str) -> &'a str`를 작성하고,
왜 라이프타임 생략이 가능한지/불가능한지 설명을 덧붙이세요.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
fn largest<T: PartialOrd + Copy>(list: &[T]) -> T {
    let mut largest = list[0];
    for &item in list {
        if item > largest {
            largest = item;
        }
    }
    largest
}
```

### 응용 정답 예시

```rust
trait Notifiable {
    fn message(&self) -> String;
}

struct Email {
    subject: String,
}

impl Notifiable for Email {
    fn message(&self) -> String {
        format!("[email] {}", self.subject)
    }
}
```

### 도전 정답 예시

```rust
fn first_token(line: &str) -> &str {
    line.split_whitespace().next().unwrap_or("")
}
```

해설:

- 입력 참조 하나에서 출력 참조 하나가 나오는 형태는 라이프타임 생략 규칙으로 추론됩니다.

## 오답 예시 3종 + 해설

### 오답 1) 제네릭에 불필요한 과도한 bound

문제점: 쓸 수 있는 타입이 과도하게 줄어듭니다.
개선: 함수 내부 연산에 필요한 최소 trait만 선언하세요.

### 오답 2) 트레잇 없이 `match`로 타입 분기

문제점: 타입이 늘어날 때 수정 지점이 폭증합니다.
개선: 공통 행동은 트레잇으로 추상화하고 다형성으로 처리하세요.

### 오답 3) 라이프타임을 데이터 수명 연장으로 오해

문제점: 잘못된 참조 반환을 시도하게 됩니다.
개선: 라이프타임은 "연장"이 아니라 "관계 표기"임을 기억하세요.

## 이 장에서 꼭 가져갈 습관

1. 추상화는 최소 bound로 설계한다.
2. 행동 계약은 트레잇으로 명시한다.
3. 참조 반환 함수는 수명 관계를 먼저 생각한다.

## 미니 퀴즈 (정답 포함)

1) 제네릭에 trait bound를 붙이는 핵심 목적은?
- 정답: 임의 타입 허용이 아니라 필요한 능력만 요구해 안전한 재사용을 보장하기 위해서입니다.

2) `impl Trait`와 `T: Trait` 중 무엇을 선택해야 하나요?
- 정답: 단순 시그니처 표현엔 `impl Trait`, 타입 관계를 명시해야 하면 `T: Trait`가 유리합니다.

3) 라이프타임은 메모리 수명을 늘리는 기능인가요?
- 정답: 아니요. 참조 간 유효 범위 관계를 컴파일러에 명시하는 표기입니다.

## 학습 완료 기준

1. 최소 trait bound로 제네릭 함수를 설계한다.
2. 트레잇으로 행동 계약을 분리한다.
3. 참조 반환 함수의 수명 관계를 설명한다.

## 실전 확장 미션

1. 플러그인 형태 trait 기반 모듈 작성
2. lifetime 관련 컴파일 오류 2개 분석

## 부가 설명: 추상화 품질은 제한 조건에서 결정된다

제네릭이 강력한 이유는 넓게 열어 두어서가 아니라, 필요한 능력만 정확히 요구하기 때문입니다.
바운드를 최소화하면 호출 가능한 타입 범위가 넓어지고 API 재사용성이 올라갑니다.

라이프타임은 초반에 문법처럼 외우기 쉽지만, 실제로는 참조 관계를 설계하는 도구입니다.
반환 참조가 어디에서 왔는지 말로 설명해 보는 연습을 하면 이해 속도가 빨라집니다.

## 아주 사소한 것까지: 용어 미니 사전

1. generic: 타입을 매개변수로 일반화합니다.
2. trait bound: 제네릭 타입이 가져야 할 능력 제약입니다.
3. trait: 행동 계약(인터페이스)입니다.
4. lifetime: 참조 유효 범위 관계 표기입니다.
5. impl Trait: 단순 시그니처 추상화 문법입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 추상화 경계

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 트레잇 계약를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 수명 관계에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: API 재사용성를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
