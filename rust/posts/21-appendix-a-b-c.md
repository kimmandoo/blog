# 21. 부록 A-C 핵심 정리

부록 A-C는 "사전"처럼 보이지만,
실전에서 자주 헷갈리는 문법을 빠르게 교정하는 도구입니다.
특히 키워드와 derive 트레잇은 디버깅 속도를 직접 좌우합니다.

## 핵심 개념과 원리

### 1) 키워드 정확도

`move`, `crate`, `super`, `dyn`, `where`, `async` 같은 키워드는
한 글자만 달라도 의미가 크게 달라집니다.

### 2) 연산자와 우선순위

복잡한 조건식은 괄호로 의도를 명시하는 습관이 중요합니다.
연산자 우선순위를 외우기보다 "읽기 쉬운 표현"을 우선하세요.

### 3) derive 트레잇은 자동화 계약

`Debug`, `Clone`, `PartialEq`, `Eq`, `Hash`, `Default` 등은
타입이 어떤 생태계 동작을 지원하는지 선언합니다.

## 기술적인 심화 설명

### derive를 무의식적으로 붙이지 않기

예: `Clone`을 붙이면 값 복제가 쉬워지지만,
큰 구조체에서 비용이 커질 수 있습니다.
"필요한 트레잇만 derive"가 원칙입니다.

### `Hash` + `Eq` 짝

`HashMap` 키 타입은 보통 `Eq + Hash`가 함께 필요합니다.
한쪽만 생각하면 컴파일 오류를 자주 만나게 됩니다.

## 대표 코드

```rust
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
struct UserKey {
    org_id: u64,
    user_id: u64,
}
```

## 실습 문제 (3단계)

### 1) 기본

도메인 타입 하나를 만들고 `Debug`, `PartialEq`를 derive해 비교/출력을 확인.

### 2) 응용

같은 타입을 `HashMap` 키로 쓰기 위해 필요한 derive를 추가.

### 3) 도전

derive 없이 수동 구현이 필요한 상황 하나를 만들고 이유를 정리.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
#[derive(Debug, PartialEq)]
struct Version {
    major: u8,
    minor: u8,
}
```

### 응용 정답 예시

```rust
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
struct CacheKey {
    namespace: String,
    id: u64,
}
```

### 도전 정답 방향

부동소수점 포함 구조체는 `Eq` 자동 파생이 불가할 수 있으므로,
도메인 규칙에 맞는 수동 비교 전략이 필요합니다.

## 오답 예시 3종 + 해설

### 오답 1) 필요 없는 derive 남발

문제점: 타입 의미와 비용 모델이 흐려집니다.
개선: 실제 요구되는 trait만 선택하세요.

### 오답 2) 연산자 우선순위에만 의존

문제점: 코드 리뷰에서 오해가 잦습니다.
개선: 괄호로 의도를 명확히 표현하세요.

### 오답 3) 키워드 의미를 추측으로 사용

문제점: 미묘한 버그/컴파일 오류를 반복합니다.
개선: 부록 표를 기준으로 빠르게 확인하는 습관을 가지세요.

## 미니 퀴즈 (정답 포함)

1) derive를 무조건 많이 붙이지 말아야 하는 이유는?
- 정답: 타입 의미와 비용 모델이 흐려지고 불필요한 복제/제약이 생길 수 있기 때문입니다.

2) `HashMap` 키 타입에 자주 필요한 trait 조합은?
- 정답: 보통 `Eq`와 `Hash`가 함께 필요합니다.

3) 연산자 우선순위를 외우는 것보다 중요한 실무 습관은?
- 정답: 괄호로 의도를 명시해 읽는 사람의 오해를 줄이는 것입니다.

## 학습 완료 기준

1. 자주 쓰는 키워드/derive 의미를 정확히 구분한다.
2. 연산자 우선순위를 괄호로 명확히 표현한다.
3. HashMap 키 타입 trait 요구를 이해한다.

## 실전 확장 미션

1. 팀 공용 derive 가이드 작성
2. 키워드 오해 사례 5개 정리

## 부가 설명: 부록 A-C를 암기표가 아닌 참조 도구로 쓰는 법

이 부록은 한 번 읽고 외우는 자료가 아니라, 막힐 때 즉시 찾아보는 작업용 레퍼런스입니다.
자주 헷갈리는 키워드와 derive 조합을 개인 노트로 추려 두면 실전 속도가 빠르게 올라갑니다.

특히 연산자 우선순위는 암기보다 표현 습관이 중요합니다.
괄호를 적극 사용해 의도를 명확히 하면 팀 리뷰 품질도 함께 올라갑니다.

## 아주 사소한 것까지: 용어 미니 사전

1. keyword: 언어 문법상 예약된 식별자입니다.
2. operator precedence: 연산 우선순위 규칙입니다.
3. derive(Debug): 디버그 출력 구현 자동 생성입니다.
4. derive(Clone): 값 복제 구현 자동 생성입니다.
5. derive(Eq/Hash): 동등성/해시 구현 자동 생성입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 키워드 정확도

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 연산자 우선순위를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: derive 선택에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 레퍼런스 활용를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
