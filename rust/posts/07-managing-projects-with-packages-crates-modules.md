# 07. 패키지, 크레이트, 모듈

Chapter 7은 "파일 나누기" 수업이 아닙니다.
패키지/크레이트/모듈을 이용해서 변경이 쉬운 구조를 만드는 설계 장입니다.
작게는 import 정리, 크게는 공개 API 경계까지 여기서 결정됩니다.

## 핵심 개념과 원리

### 1) 패키지(package)와 크레이트(crate)

- package: `Cargo.toml` 기준 배포/빌드 단위
- crate: 컴파일 단위(바이너리 또는 라이브러리)

하나의 package는 여러 binary crate를 가질 수 있고,
보통 `src/lib.rs`는 library crate 루트, `src/main.rs`는 binary crate 루트 역할을 합니다.

### 2) 모듈(module)은 책임 경계

모듈은 단순 디렉터리 분리가 아니라 "어떤 지식을 숨길지"를 정하는 도구입니다.
변경 가능성이 높은 내부 구현은 감추고, 안정적인 인터페이스만 공개해야 합니다.

### 3) `pub`는 최소한으로

처음부터 다 공개하면 사용은 편하지만, 나중에 리팩터링 비용이 폭증합니다.
Rust는 기본 비공개이기 때문에 "안전한 기본값"을 제공합니다.

## 기술적인 심화 설명

### 경로(`crate::`, `super::`, `self::`)를 읽는 힘

- `crate::`: 크레이트 루트 기준 절대 경로
- `super::`: 부모 모듈
- `self::`: 현재 모듈

팀 기준으로 경로 스타일을 통일하면 코드 리뷰 속도가 올라갑니다.
대규모 프로젝트에서는 `crate::` 절대 경로 선호가 많습니다.

### `use`는 "단축"이지 "노출"이 아니다

`use`는 경로를 짧게 만들 뿐, 접근 제어를 바꾸지 않습니다.
접근 제어는 여전히 `pub`/비공개 규칙이 결정합니다.

### Kotlin 패키지 시스템과 비교

Kotlin도 패키지/visibility가 있지만,
Rust는 모듈 트리와 `pub` 규칙이 API 경계를 훨씬 명시적으로 드러냅니다.
특히 라이브러리 개발에서 "무엇을 약속하고 무엇을 숨길지"가 코드에 선명하게 남습니다.

## 대표 코드

```rust
// src/lib.rs
pub mod restaurant;

// src/restaurant/mod.rs
pub mod hosting;
mod serving;

// src/restaurant/hosting.rs
pub fn add_to_waitlist() {
    println!("added");
}
```

```rust
// src/main.rs
use my_app::restaurant::hosting;

fn main() {
    hosting::add_to_waitlist();
}
```

## 실습 문제 (3단계)

### 1) 기본: 모듈 분리

`math` 모듈을 만들어 `add`, `sub` 함수를 분리하고
`main`에서 호출하세요.

### 2) 응용: 공개 API 최소화

`math` 내부에 `normalize_input` 헬퍼 함수를 만들되
외부에서는 접근하지 못하도록 숨기세요.

### 3) 도전: 라이브러리 + 바이너리 분리

`src/lib.rs`에 계산 로직을 두고,
`src/main.rs`는 CLI 입력/출력만 담당하도록 리팩터링하세요.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
// src/math.rs
pub fn add(a: i32, b: i32) -> i32 { a + b }
pub fn sub(a: i32, b: i32) -> i32 { a - b }
```

```rust
// src/main.rs
mod math;

fn main() {
    println!("{}", math::add(3, 2));
}
```

### 응용 정답 예시

```rust
// src/math.rs
fn normalize_input(value: i32) -> i32 {
    value.clamp(-10_000, 10_000)
}

pub fn add(a: i32, b: i32) -> i32 {
    normalize_input(a) + normalize_input(b)
}
```

해설:

- `normalize_input`를 비공개로 유지해 API 표면을 줄였습니다.

### 도전 정답 방향

- `lib.rs`: 순수 계산 함수 + 테스트
- `main.rs`: 인자 파싱, 출력, 에러 메시지

이 분리를 하면 테스트는 `lib` 중심으로 빠르게 진행할 수 있습니다.

## 오답 예시 3종 + 해설

### 오답 1) 모든 모듈/함수에 `pub` 남발

문제점: 내부 구현까지 외부 의존점이 생겨 리팩터링이 어려워집니다.
개선: 외부에서 써야 하는 최소 인터페이스만 공개하세요.

### 오답 2) `main.rs`에 도메인 로직 집중

문제점: 테스트 작성이 불편하고 재사용이 어렵습니다.
개선: 핵심 로직은 `lib.rs`/모듈로 이동하고 `main`은 조립 계층으로 둡니다.

### 오답 3) 모듈 경계를 파일 크기 기준으로만 분리

문제점: 책임이 섞여서 "어디를 수정해야 하는지"가 불명확해집니다.
개선: 기능/도메인 책임 기준으로 모듈을 설계하세요.

## 이 장에서 꼭 가져갈 습관

1. 모듈은 책임 경계로 설계한다.
2. 공개 API를 의도적으로 최소화한다.
3. `lib`와 `main`을 분리해 테스트 가능성을 높인다.

## 미니 퀴즈 (정답 포함)

1) package와 crate의 차이는 무엇인가요?
- 정답: package는 `Cargo.toml` 기준 관리 단위이고, crate는 컴파일 단위(바이너리/라이브러리)입니다.

2) `use`와 `pub`의 역할 차이는?
- 정답: `use`는 경로 단축, `pub`는 접근 제어(공개 범위) 설정입니다.

3) `main`에 로직을 몰아넣지 말아야 하는 이유는?
- 정답: 테스트/재사용이 어려워지고 변경 영향 범위가 과도하게 커지기 때문입니다.

## 학습 완료 기준

1. package/crate/module 차이를 설명한다.
2. `pub` 최소화 원칙으로 API 표면을 줄인다.
3. `lib`와 `main` 책임 분리를 구현한다.

## 실전 확장 미션

1. workspace로 core/cli 분리
2. 모듈 트리 다이어그램 직접 작성

## 부가 설명: 모듈 분리는 파일 분리가 아니다

파일을 나눴는데도 복잡하다면 보통 책임 경계가 잘못된 경우입니다.
"같이 바뀌는 코드"를 기준으로 묶고, "다른 속도로 바뀌는 코드"를 분리하면 모듈 구조가 훨씬 안정됩니다.

또한 공개 API를 줄이는 선택은 당장 불편해 보여도 미래 리팩터링 자유도를 확보하는 투자입니다.
외부에서 꼭 필요한 것만 열어 두는 습관이 유지보수 난이도를 낮춰 줍니다.

## 아주 사소한 것까지: 용어 미니 사전

1. package: Cargo.toml 기준 관리 단위입니다.
2. crate: 컴파일 단위(바이너리/라이브러리)입니다.
3. module: 코드 책임 경계 단위입니다.
4. pub: 외부 공개 접근 제어자입니다.
5. crate:: / super:: / self::: 절대/부모/현재 경로 지정 문법입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 모듈 경계

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 공개 API 설계를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 의존 방향에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 리팩터링 비용 제어를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
