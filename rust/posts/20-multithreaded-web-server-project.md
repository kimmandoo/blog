# 20. 멀티스레드 웹 서버 프로젝트

마지막 프로젝트 장은 지금까지 배운 내용을 한 시스템으로 묶는 단계입니다.
핵심은 "HTTP를 완벽히 구현"하는 것이 아니라,
요청 처리 구조, 스레드 풀, 종료 전략을 안전하게 설계하는 것입니다.

## 핵심 개념과 원리

### 1) 요청 수락 루프

`TcpListener`에서 연결을 받아 핸들러에 전달합니다.
이때 I/O 실패를 로깅하고 다음 요청으로 넘어가는 탄력성이 필요합니다.

### 2) 스레드 풀

요청마다 새 스레드를 만들면 비용이 큽니다.
고정 워커 스레드에 작업을 큐잉하면 지연과 자원 사용이 안정됩니다.

### 3) graceful shutdown

서버 종료 시 워커에게 종료 신호를 보내고 `join`으로 회수해야
중간 작업 유실과 리소스 누수를 줄일 수 있습니다.

## 기술적인 심화 설명

### ThreadPool API 설계

`execute(F)`에서 `F: FnOnce() + Send + 'static` 경계를 명확히 선언하면
큐에 들어가는 작업의 스레드 안전성이 보장됩니다.

### 백프레셔 관점

큐가 무한정 쌓이면 응답 지연이 폭증합니다.
학습 단계에서도 큐 길이 제한, 타임아웃, 간단한 거부 정책을 생각해 보는 것이 좋습니다.

## 대표 코드

```rust
use std::net::TcpListener;

fn main() {
    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();
    let pool = ThreadPool::new(4);

    for stream in listener.incoming() {
        let stream = match stream {
            Ok(s) => s,
            Err(e) => {
                eprintln!("connection error: {e}");
                continue;
            }
        };

        pool.execute(|| {
            // handle_connection(stream)
        });
    }
}
```

## 실습 문제 (3단계)

### 1) 기본

`/` 요청은 200, 그 외는 404를 반환하는 라우팅 구현.

### 2) 응용

`/sleep` 경로에서 3초 지연 후 응답하고, 다른 요청이 막히지 않음을 확인.

### 3) 도전

종료 신호를 받으면 워커에 종료 메시지를 보내고 정상 종료하도록 구현.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
let status_line = if request_line == "GET / HTTP/1.1" {
    "HTTP/1.1 200 OK"
} else {
    "HTTP/1.1 404 NOT FOUND"
};
```

### 응용 정답 예시

```rust
if request_line == "GET /sleep HTTP/1.1" {
    std::thread::sleep(std::time::Duration::from_secs(3));
}
```

### 도전 정답 방향

`enum Message { NewJob(Job), Terminate }`를 사용해
Drop 시 `Terminate`를 워커 수만큼 전송한 뒤 join합니다.

## 오답 예시 3종 + 해설

### 오답 1) 요청당 새 스레드 생성

문제점: 부하 시 스레드 폭증으로 성능이 급격히 악화됩니다.
개선: 고정 크기 스레드 풀로 제어하세요.

### 오답 2) connection 오류에서 즉시 서버 종료

문제점: 일시적 네트워크 오류로 전체 서비스가 중단됩니다.
개선: 오류 로깅 후 루프를 지속하세요.

### 오답 3) 종료 시 워커 join 생략

문제점: 처리 중 작업이 손실될 수 있습니다.
개선: 종료 메시지 + join으로 마무리 경로를 보장하세요.

## 미니 퀴즈 (정답 포함)

1) 요청당 스레드 생성 대신 스레드 풀을 쓰는 이유는?
- 정답: 스레드 생성/파괴 비용을 줄이고 부하 상황에서 자원 사용을 안정화하기 위해서입니다.

2) graceful shutdown이 필요한 이유는?
- 정답: 처리 중 작업 유실과 리소스 누수를 줄이고 정상 종료를 보장하기 위해서입니다.

3) 연결 오류가 발생했을 때 서버를 바로 종료하면 생기는 문제는?
- 정답: 일시적 오류에도 전체 서비스 가용성이 급격히 떨어집니다.

## 학습 완료 기준

1. 스레드 풀 기반 요청 처리 구조를 설명한다.
2. 핸들러/라우팅/응답 생성을 분리한다.
3. graceful shutdown 흐름을 구현한다.

## 실전 확장 미션

1. 정적 파일 서빙 추가
2. 요청 타임아웃/큐 제한 정책 실험

## 부가 설명: 서버 프로젝트에서 학습자가 자주 놓치는 것

HTTP 응답을 반환하는 데 성공해도 서버가 안정적이라는 뜻은 아닙니다.
오류 처리, 큐 포화, 종료 시그널, 작업 회수 같은 운영 시나리오를 함께 점검해야 실제 실력이 됩니다.

이 장에서는 처리량보다 구조 일관성을 우선하세요.
핸들러 분리, 워커 생명주기, 종료 프로토콜이 명확하면 이후 기능 확장이 훨씬 쉬워집니다.

## 아주 사소한 것까지: 용어 미니 사전

1. TcpListener: TCP 연결 수락 서버 소켓입니다.
2. worker thread: 큐에서 작업을 꺼내 실행하는 스레드입니다.
3. backpressure: 처리량 한계를 넘는 입력을 제어하는 전략입니다.
4. graceful shutdown: 작업 손실 최소화 종료 절차입니다.
5. request routing: 요청 경로에 따라 핸들러를 분기하는 과정입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 서버 구조

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 워커 풀 운영를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 백프레셔에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: graceful shutdown를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
