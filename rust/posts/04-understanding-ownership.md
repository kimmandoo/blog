# 04. 소유권과 빌림의 원리

소유권은 Rust의 중심축입니다.
이 장을 제대로 이해하면 이후의 수명, 트레잇, 동시성까지 한 번에 연결됩니다.
반대로 여기서 감으로 넘기면 "왜 컴파일러가 화내는지" 계속 모르는 상태가 됩니다.

## 핵심 개념과 원리

### 1) 소유권(ownership): 값에는 단 하나의 owner가 있다

Rust의 기본 규칙:

1. 각 값은 소유자를 하나 가진다.
2. 소유자가 스코프를 벗어나면 값은 drop된다.
3. 소유권은 대입/함수 호출 시 이동(move)할 수 있다.

```rust
let s1 = String::from("hello");
let s2 = s1; // move
// println!("{s1}"); // 컴파일 오류
println!("{s2}");
```

`String`은 힙 데이터를 관리하므로 얕은 복사를 허용하면 이중 해제 위험이 생깁니다.
Rust는 move를 통해 이 문제를 컴파일 타임에 제거합니다.

### 2) 빌림(borrowing): 소유권을 옮기지 않고 참조로 접근

```rust
fn len_of(s: &String) -> usize {
    s.len()
}
```

`&T`는 불변 참조, `&mut T`는 가변 참조입니다.
규칙이 엄격합니다.

- 같은 시점에 불변 참조 여러 개는 가능
- 같은 시점에 가변 참조는 하나만 가능
- 불변 참조와 가변 참조 동시 공존은 불가

이 규칙이 런타임 락 없이 데이터 경합을 차단합니다.

### 3) 슬라이스(slice): 복사 없이 부분 데이터 참조

```rust
fn first_word(s: &str) -> &str {
    for (i, ch) in s.char_indices() {
        if ch == ' ' {
            return &s[..i];
        }
    }
    s
}
```

`&str`은 UTF-8 바이트 배열의 뷰(view)입니다.
슬라이스를 쓰면 문자열 일부를 복사하지 않고도 안전하게 다룰 수 있습니다.

## 기술적인 심화 설명

### 왜 C/C++의 포인터와 감각이 다른가?

C/C++에서는 포인터 유효성 관리가 개발자 책임입니다.
Rust에서는 참조의 유효 범위를 컴파일러가 추론해 강제합니다.
그래서 dangling reference 가능성이 원천 차단됩니다.

### Kotlin과 비교하면?

Kotlin은 GC 기반이라 소유권 이전/이중 해제를 직접 의식하지 않아도 됩니다.
대신 Rust는 GC 없이도 메모리 안전성을 얻기 위해
소유권/빌림/수명 규칙을 타입 시스템에 포함시킵니다.
즉, "실행 중 관리"를 "컴파일 시 검증"으로 옮긴 셈입니다.

### NLL(Non-Lexical Lifetimes) 감각

현대 Rust 컴파일러는 참조의 실제 마지막 사용 시점을 기준으로 수명을 계산합니다.
그래서 예전보다 유연하지만, 규칙 자체가 사라진 것은 아닙니다.
"더 이상 사용하지 않는 시점"을 코드로 명확히 보여 주는 습관이 여전히 중요합니다.

## 대표 코드

```rust
fn append_exclamation(s: &mut String) {
    s.push('!');
}

fn main() {
    let mut message = String::from("hello");

    let len = message.len();
    println!("before: {message} ({len})");

    append_exclamation(&mut message);
    println!("after: {message}");
}
```

핵심 포인트:

- 읽기 전용 접근과 수정 접근을 분리했습니다.
- `&mut`는 최소 범위에서만 사용했습니다.

## 실습 문제 (3단계)

### 1) 기본: move와 clone 구분하기

`String` 두 개를 다루는 코드에서,
어떤 경우는 move, 어떤 경우는 `clone`이 필요한지 직접 실험해 보세요.
"왜 clone이 필요한가"를 한 줄 주석으로 설명하세요.

### 2) 응용: 빌림 기반 문자열 처리 함수 만들기

다음 시그니처를 구현하세요.

```rust
fn normalize_name(input: &str) -> String
```

조건:

- 앞뒤 공백 제거
- 빈 문자열이면 `"anonymous"` 반환
- 그 외에는 첫 글자만 대문자

### 3) 도전: 슬라이스 안전성 검증

`fn first_token(line: &str) -> &str`를 작성하고,
공백/탭/빈 문자열 케이스를 테스트 5개 이상으로 검증하세요.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
let a = String::from("rust");
let b = a; // move
// println!("{a}"); // 불가

let c = String::from("lang");
let d = c.clone(); // 깊은 복사
println!("{c} {d}");
```

해설:

- move는 소유권 이전, clone은 데이터 복제입니다.
- clone은 비용이 있으므로 꼭 필요할 때만 사용합니다.

### 응용 정답 예시

```rust
fn normalize_name(input: &str) -> String {
    let trimmed = input.trim();
    if trimmed.is_empty() {
        return "anonymous".to_string();
    }

    let mut chars = trimmed.chars();
    let first = chars.next().unwrap().to_uppercase().to_string();
    let rest = chars.as_str().to_lowercase();
    format!("{first}{rest}")
}
```

### 도전 정답 예시

```rust
fn first_token(line: &str) -> &str {
    for (i, ch) in line.char_indices() {
        if ch == ' ' || ch == '\t' {
            return &line[..i];
        }
    }
    line
}

#[cfg(test)]
mod tests {
    use super::first_token;

    #[test]
    fn token_basic() {
        assert_eq!(first_token("rust book"), "rust");
    }

    #[test]
    fn token_tab() {
        assert_eq!(first_token("rust\tbook"), "rust");
    }
}
```

## 오답 예시 3종 + 해설

### 오답 1) move 이후 원본 사용

```rust
let s1 = String::from("hello");
let s2 = s1;
println!("{s1}");
```

문제점: 소유권이 이동했는데 원본을 다시 사용해 컴파일 오류가 발생합니다.
개선: 원본을 계속 쓸 필요가 있으면 참조를 전달하거나 필요한 경우만 `clone`합니다.

### 오답 2) 가변 참조 중복 생성

```rust
let mut s = String::from("x");
let r1 = &mut s;
let r2 = &mut s;
```

문제점: 같은 시점에 여러 `&mut`가 존재해 데이터 경합 가능성이 생깁니다.
개선: 가변 참조의 생존 범위를 줄이거나 순차적으로 사용하세요.

### 오답 3) 인덱스로 문자열 자르기

```rust
let s = String::from("안녕");
let part = &s[0..1];
```

문제점: UTF-8 경계가 깨질 수 있어 panic 가능성이 있습니다.
개선: `char_indices`, `chars`, `split_whitespace` 등 문자 경계 인식 API를 사용하세요.

## 이 장에서 꼭 가져갈 습관

1. 소유권 이동을 두려워하지 말고 흐름을 추적한다.
2. 참조의 생존 범위를 짧게 유지한다.
3. 문자열은 바이트가 아닌 UTF-8 경계 관점으로 다룬다.

## 미니 퀴즈 (정답 포함)

1) `String` 대입 시 기본 동작이 복사가 아니라 move인 이유는?
- 정답: 힙 메모리 이중 해제 위험을 막고 소유권을 단일화하기 위해서입니다.

2) 같은 시점에 `&mut` 참조를 여러 개 허용하지 않는 핵심 이유는?
- 정답: 데이터 경쟁 가능성을 컴파일 단계에서 차단하기 위해서입니다.

3) `&str` 슬라이스를 쓰는 장점은?
- 정답: 복사 없이 문자열 일부를 안전하게 참조할 수 있어 성능과 안전성을 동시에 확보할 수 있습니다.

## 부가 설명: borrow checker를 적으로 보지 않는 법

소유권 오류는 실패가 아니라 설계 힌트입니다. "누가 소유해야 하는가"와 "누가 잠깐 빌려 쓰는가"를 먼저 정하면,
컴파일러 메시지가 제약이 아니라 구조 안내서처럼 읽히기 시작합니다.

또한 문자열 처리에서 UTF-8 경계를 의식하는 습관은 초반에 꼭 잡아야 합니다.
영문 중심 예제에서 잘 동작하던 코드가 다국어 입력에서 깨지는 문제를 미리 예방할 수 있습니다.

## 아주 사소한 것까지: 용어 미니 사전

1. move: 소유권이 다른 변수로 이전됩니다.
2. borrow: 소유권을 옮기지 않고 참조로 접근합니다.
3. &T / &mut T: 불변 참조 / 가변 참조입니다.
4. slice: 데이터 일부를 복사 없이 참조하는 뷰입니다.
5. dangling reference: 해제된 메모리를 가리키는 잘못된 참조입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 소유권 모델

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 참조 규칙를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 수명 감각에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 문자열 슬라이스 안전성를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
