# 09. 에러 처리 전략

에러 처리는 "문제가 생겼다"를 출력하는 기술이 아니라,
실패를 설계 가능한 경로로 바꾸는 기술입니다.
Chapter 9를 제대로 이해하면 프로젝트가 커져도 코드가 덜 무너집니다.

## 핵심 개념과 원리

### 1) `panic!`은 복구 불가능할 때만

`panic!`은 현재 스레드를 즉시 종료합니다.
즉, 호출자에게 선택권을 주지 않습니다.
사용자 입력, 파일 없음, 네트워크 일시 장애처럼 복구 가능한 실패는 `Result`로 다뤄야 합니다.

### 2) `Result<T, E>`는 함수 계약이다

```rust
fn read_username(path: &str) -> Result<String, std::io::Error>
```

이 시그니처 하나로 다음이 명확해집니다.

- 성공하면 `String`
- 실패하면 `io::Error`

호출자는 `match`/`?`를 통해 실패 경로를 강제로 고려하게 됩니다.

### 3) `?` 연산자는 "숨김"이 아니라 "전파"다

`?`는 에러를 무시하는 문법이 아닙니다.
오류를 현재 함수의 반환 타입으로 변환해 상위로 전달하는 문법입니다.

## 기술적인 심화 설명

### 에러 타입을 언제 커스텀해야 하나?

초반에는 `io::Error`, `ParseIntError` 같은 표준 에러로도 충분합니다.
하지만 도메인 규칙이 생기면 enum 기반 커스텀 에러가 필요합니다.

```rust
enum AppError {
    Io(std::io::Error),
    EmptyInput,
    InvalidFormat,
}
```

### 컨텍스트를 붙여야 디버깅이 빨라진다

동일한 `No such file or directory`라도
"어떤 파일을 읽다가" 실패했는지를 메시지에 포함해야 운영에서 바로 대응 가능합니다.

### Kotlin 예외 처리와 비교

Kotlin은 예외를 throw/catch로 처리하는 흐름이 일반적입니다.
Rust는 실패를 타입 시그니처에서 노출하기 때문에,
"어디서 실패 가능한가"가 더 앞단에서 드러납니다.

## 대표 코드

```rust
use std::fs;
use std::io;

fn read_username(path: &str) -> Result<String, io::Error> {
    let content = fs::read_to_string(path)?;
    Ok(content.trim().to_string())
}
```

## 실습 문제 (3단계)

### 1) 기본: 파일 읽기 실패 처리

파일 경로를 입력받아 내용을 읽는 함수를 작성하세요.
파일이 없으면 사용자 친화 메시지를 출력하고 종료하지 말고 재입력 받으세요.

### 2) 응용: 파싱 + 도메인 검증

문자열에서 포트 번호를 읽어 `u16`으로 변환하세요.

- 빈 입력: 별도 오류
- 숫자 아님: 별도 오류
- 0: 별도 오류

### 3) 도전: 커스텀 에러 타입

위 로직을 `enum ConfigError`로 통합하고,
`Display` 구현으로 사람이 읽기 쉬운 메시지를 만드세요.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
use std::fs;

fn load_text(path: &str) -> Result<String, String> {
    fs::read_to_string(path)
        .map(|v| v.trim().to_string())
        .map_err(|e| format!("failed to read '{path}': {e}"))
}
```

### 응용 정답 예시

```rust
fn parse_port(input: &str) -> Result<u16, String> {
    let trimmed = input.trim();
    if trimmed.is_empty() {
        return Err("input is empty".to_string());
    }
    let port: u16 = trimmed.parse().map_err(|_| "not a number".to_string())?;
    if port == 0 {
        return Err("port must be 1..=65535".to_string());
    }
    Ok(port)
}
```

### 도전 정답 예시

```rust
use std::fmt::{Display, Formatter};

#[derive(Debug)]
enum ConfigError {
    Empty,
    NotNumber,
    OutOfRange,
}

impl Display for ConfigError {
    fn fmt(&self, f: &mut Formatter<'_>) -> std::fmt::Result {
        match self {
            ConfigError::Empty => write!(f, "input is empty"),
            ConfigError::NotNumber => write!(f, "input is not a number"),
            ConfigError::OutOfRange => write!(f, "port must be 1..=65535"),
        }
    }
}
```

## 오답 예시 3종 + 해설

### 오답 1) 사용자 입력 실패에 `panic!` 사용

문제점: 복구 가능한 상황에서 앱이 바로 종료됩니다.
개선: 입력 오류는 `Result`로 반환하고 재시도 경로를 제공합니다.

### 오답 2) `unwrap` 연쇄

문제점: 실패 위치와 원인이 흐려지고 장애가 커집니다.
개선: `?` + 명시적 에러 변환(`map_err`)로 문맥을 붙이세요.

### 오답 3) 모든 실패를 문자열 하나로 뭉개기

문제점: 호출자가 실패 원인별 대응을 할 수 없습니다.
개선: enum 에러로 유형을 분리하고, `Display`는 사람용 메시지로 유지하세요.

## 이 장에서 꼭 가져갈 습관

1. 복구 가능 실패는 반드시 `Result`로 설계한다.
2. `?`를 쓰되 오류 문맥을 잃지 않는다.
3. 도메인 에러는 enum으로 분리한다.

## 미니 퀴즈 (정답 포함)

1) 사용자 입력 오류에 `panic!` 대신 `Result`를 우선해야 하는 이유는?
- 정답: 복구 가능한 실패를 호출자에게 전달해 재시도/대체 경로를 설계할 수 있기 때문입니다.

2) `?` 연산자의 정확한 역할은?
- 정답: 오류를 무시하는 것이 아니라 현재 함수의 에러 타입으로 변환해 상위로 전파하는 것입니다.

3) 문자열 하나로 모든 에러를 처리하면 생기는 문제는?
- 정답: 실패 원인별 분기 대응이 어려워지고 디버깅 및 운영 대응 속도가 떨어집니다.

## 학습 완료 기준

1. panic과 Result 경계를 구분한다.
2. `?` 전파와 `map_err` 문맥 추가를 활용한다.
3. 커스텀 에러 enum을 설계한다.

## 실전 확장 미션

1. 오류 코드 체계(AppError) 도입
2. 로그 메시지 표준 포맷 정의

## 부가 설명: 에러 메시지는 운영 도구다

학습 단계에서는 단순 메시지로 충분해 보이지만, 실제 서비스에서는 "무엇을 하다 실패했는지"가 핵심입니다.
같은 에러 타입이라도 파일 경로, 입력 값, 요청 문맥을 함께 남겨야 원인 추적이 빨라집니다.

또한 에러를 너무 이른 단계에서 문자열로 뭉개면 상위 계층이 대응 전략을 선택할 수 없습니다.
가능하면 타입 정보는 유지하고, 표시 직전 계층에서 사람 친화 메시지로 변환하세요.

## 아주 사소한 것까지: 용어 미니 사전

1. panic!: 복구 불가능한 상황에서 프로그램 흐름을 중단합니다.
2. ? 연산자: 에러를 상위 호출자로 전파합니다.
3. map_err: 에러 타입/메시지를 변환합니다.
4. custom error enum: 도메인별 실패 유형을 모델링합니다.
5. Display: 사람 친화적 에러 메시지 포맷을 제공합니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 에러 계층

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 복구 전략를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 문맥 로그에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 장애 대응 속도를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
