# 19. 고급 기능: unsafe, 매크로, 고급 타입

이 장은 Rust의 "안전 울타리 바깥"을 다루는 장입니다.
핵심 원칙은 단 하나입니다: 위험한 기능을 쓰더라도 안전한 인터페이스로 감싸서 팀 전체의 안전성을 유지한다.

## 핵심 개념과 원리

### 1) unsafe는 기능이 아니라 책임 선언

`unsafe` 블록 안에서는 컴파일러가 보장하지 않는 가정을 개발자가 증명해야 합니다.
그래서 범위를 가능한 좁게 유지하고, 근거를 문서화해야 합니다.

### 2) 고급 타입으로 모델 정확도 강화

타입 별칭과 뉴타입은 런타임 비용보다 설계 명확성을 위해 쓰입니다.
특히 뉴타입은 서로 다른 의미의 동일 원시 타입을 분리할 수 있습니다.

### 3) 매크로는 반복 패턴 제거 도구

함수/제네릭으로 해결되지 않는 문법 반복에만 도입해야 합니다.
매크로 남용은 디버깅 난이도를 크게 올립니다.

## 기술적인 심화 설명

### unsafe 5가지 핵심 동작 감각

raw pointer 역참조, unsafe 함수 호출, mutable static 접근, unsafe trait 구현, union field 접근.
이 동작들은 모두 안전성 가정이 필요합니다.

### FFI 경계

C 라이브러리 호출은 흔히 unsafe가 필요합니다.
경계 함수에서 검증/변환을 끝내고 내부는 safe Rust로 유지하는 구조가 좋습니다.

## 대표 코드

```rust
fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = values.len();
    let ptr = values.as_mut_ptr();
    assert!(mid <= len);

    unsafe {
        (
            std::slice::from_raw_parts_mut(ptr, mid),
            std::slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}
```

## 실습 문제 (3단계)

### 1) 기본

타입 별칭과 뉴타입 각각을 사용해 사용자 ID를 모델링해 보세요.

### 2) 응용

unsafe 블록을 사용하는 함수를 작성하고, 안전 래퍼 API를 별도 제공하세요.

### 3) 도전

중복되는 assert 패턴을 줄이는 선언적 매크로를 하나 작성하세요.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
type UserIdRaw = u64;
struct UserId(u64);
```

해설: 타입 별칭은 구분이 약하고, 뉴타입은 완전히 다른 타입으로 취급됩니다.

### 응용 정답 방향

unsafe 코드는 private 함수에 가두고,
public 함수에서 인자 검증 후 호출하는 구조를 사용합니다.

### 도전 정답 예시

```rust
macro_rules! assert_non_empty {
    ($v:expr) => {
        assert!(!$v.is_empty(), "value must not be empty");
    };
}
```

## 오답 예시 3종 + 해설

### 오답 1) unsafe 범위를 함수 전체로 확장

문제점: 위험 영역이 과도하게 넓어 검증이 어려워집니다.
개선: 필요한 최소 줄에만 unsafe를 적용하세요.

### 오답 2) 뉴타입 없이 의미 다른 값 혼용

문제점: `UserId`, `OrderId`를 같은 `u64`로 섞는 실수가 생깁니다.
개선: 뉴타입으로 의미를 강제 분리하세요.

### 오답 3) 매크로로 일반 함수 로직까지 대체

문제점: 컴파일 오류 메시지가 난해해지고 유지보수가 어려워집니다.
개선: 함수/제네릭으로 가능한 것은 함수로 유지하세요.

## 미니 퀴즈 (정답 포함)

1) unsafe 블록을 최소 범위로 유지해야 하는 이유는?
- 정답: 검증해야 할 위험 영역을 줄여 안전성 증명과 코드 리뷰를 쉽게 만들기 위해서입니다.

2) 뉴타입 패턴의 실무 가치 한 가지는?
- 정답: 같은 원시 타입이라도 의미가 다른 값을 타입 수준에서 분리해 혼용 실수를 막습니다.

3) 매크로 도입 기준은 무엇인가요?
- 정답: 함수/제네릭으로 해결하기 어려운 문법 반복 패턴에서만 제한적으로 도입해야 합니다.

## 부가 설명: 고급 기능은 성능보다 책임 경계가 먼저다

unsafe/매크로/고급 타입은 코드 힘을 크게 높이지만, 검증 부담도 함께 커집니다.
그래서 도입 기준을 문서로 남기고, 팀이 같은 기준으로 리뷰할 수 있게 만드는 것이 필수입니다.

특히 unsafe 코드는 "작동한다"보다 "안전 근거를 설명할 수 있다"가 완료 조건입니다.
근거를 설명할 수 없다면 범위를 더 줄이거나 safe 대안을 먼저 검토하세요.

## 아주 사소한 것까지: 용어 미니 사전

1. unsafe: 컴파일러 보장 밖의 동작을 수동으로 책임지는 영역입니다.
2. raw pointer: 안전성 검사가 없는 포인터 타입입니다.
3. newtype: 의미 구분을 위한 단일 필드 래퍼 타입 패턴입니다.
4. macro_rules!: 선언적 매크로 정의 문법입니다.
5. FFI: 다른 언어와 함수 경계를 연결하는 인터페이스입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 unsafe 최소화

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 고급 타입 모델링를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 매크로 도입 기준에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 안전 API 래핑를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
