# 11. 테스트 작성과 품질 확보

테스트는 "코드가 맞다"를 증명하는 절차가 아니라,
변경해도 깨지지 않는 안전망을 만드는 작업입니다.
Rust Chapter 11의 핵심은 테스트 종류를 구분해 적절한 위치에 배치하는 것입니다.

## 핵심 개념과 원리

### 1) 단위 테스트: 작은 규칙을 빠르게 검증

단위 테스트는 보통 함수/모듈 내부 규칙을 검증합니다.
속도가 빠르고 실패 지점이 좁아 디버깅에 유리합니다.

```rust
#[test]
fn adds_two() {
    assert_eq!(add(2, 2), 4);
}
```

### 2) 통합 테스트: 공개 API 사용 시나리오 검증

`tests/` 디렉터리 테스트는 라이브러리를 외부 사용자처럼 다룹니다.
즉, 내부 private 함수가 아닌 공개 인터페이스 관점의 품질을 확인합니다.

### 3) 실패 메시지는 빠를수록 좋다

실패했을 때 "무엇이, 어떤 입력에서, 왜" 깨졌는지 바로 알 수 있어야 합니다.
테스트 이름, 입력 데이터, assert 메시지를 구체적으로 작성하세요.

## 기술적인 심화 설명

### assert 계열을 용도별로 구분

- `assert!`: bool 조건
- `assert_eq!`, `assert_ne!`: 값 비교
- `should_panic`: 패닉 기대 시나리오

패닉 테스트는 정말 계약 위반에만 사용하고,
복구 가능한 실패는 `Result` 기반 테스트로 표현하세요.

### 테스트는 순수 함수 중심으로 설계해야 쉽다

I/O가 섞인 함수는 테스트가 느리고 불안정합니다.
핵심 로직을 순수 함수로 분리하면 테스트 비용이 급감합니다.

### Kotlin JUnit과의 공통점/차이

공통점은 "행동 검증"이고,
차이는 Rust가 크레이트 구조(`lib.rs`, `tests/`)와 함께 테스트 관성을 제공한다는 점입니다.
`cargo test` 한 명령으로 전체 품질 루프를 돌리기 쉽습니다.

## 대표 코드

```rust
pub fn discount(price: u32, percent: u32) -> Result<u32, String> {
    if percent > 100 {
        return Err("percent must be <= 100".to_string());
    }
    Ok(price - (price * percent / 100))
}

#[cfg(test)]
mod tests {
    use super::discount;

    #[test]
    fn discount_happy_path() {
        assert_eq!(discount(10_000, 20).unwrap(), 8_000);
    }
}
```

## 실습 문제 (3단계)

### 1) 기본: 정상/경계/오류 테스트 3개

`discount` 함수에 대해 다음 테스트를 작성하세요.

- 정상: 20%
- 경계: 0%, 100%
- 오류: 101%

### 2) 응용: 통합 테스트 추가

`tests/pricing.rs`를 만들고,
공개 함수 조합 시나리오(할인 후 배송비 계산)를 검증하세요.

### 3) 도전: 리팩터링 내성 테스트

입력 테이블 기반 반복 테스트로 확장해
새 케이스 추가가 한 줄로 가능하게 만드세요.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
#[test]
fn discount_invalid_percent() {
    let err = discount(10_000, 101).unwrap_err();
    assert_eq!(err, "percent must be <= 100");
}
```

### 응용 정답 예시

```rust
// tests/pricing.rs
use my_app::discount;

#[test]
fn final_price_with_shipping() {
    let discounted = discount(20_000, 10).unwrap();
    let shipping = 3_000;
    assert_eq!(discounted + shipping, 21_000);
}
```

### 도전 정답 예시

```rust
#[test]
fn table_driven_discount() {
    let cases = vec![(10_000, 0, 10_000), (10_000, 50, 5_000), (10_000, 100, 0)];
    for (price, percent, expected) in cases {
        assert_eq!(discount(price, percent).unwrap(), expected);
    }
}
```

개선: 외부에서 관찰 가능한 동작(입력/출력 계약) 중심으로 테스트하세요.

### 오답 3) 테스트 이름이 모호함

문제점: 실패 로그를 보고도 의미를 파악하기 어렵습니다.
개선: `when_x_then_y` 또는 조건 중심 이름으로 바꾸세요.

## 이 장에서 꼭 가져갈 습관

1. 정상/경계/실패를 세트로 테스트한다.
2. 순수 로직을 분리해 테스트를 빠르게 만든다.
3. 테스트는 구현이 아니라 계약을 검증한다.

## 미니 퀴즈 (정답 포함)

1) 단위 테스트와 통합 테스트의 가장 큰 차이는?
- 정답: 단위 테스트는 내부 작은 규칙 검증, 통합 테스트는 공개 API 사용 시나리오 검증입니다.

2) 테스트 이름을 구체적으로 써야 하는 이유는?
- 정답: 실패 로그만 보고도 조건/의도를 즉시 파악해 디버깅 시간을 줄일 수 있기 때문입니다.

3) 테스트가 구현 세부사항에 과도하게 의존하면 생기는 문제는?
- 정답: 리팩터링만 해도 테스트가 쉽게 깨져 유지보수 비용이 커집니다.

## 학습 완료 기준

1. 단위/통합 테스트를 목적에 맞게 배치한다.
2. 정상/경계/실패 케이스를 모두 작성한다.
3. 계약 중심 테스트 이름/구조를 유지한다.

## 실전 확장 미션

1. 테이블 기반 테스트 유틸 도입
2. 실패 메시지 표준 템플릿 정하기

## 부가 설명: 테스트는 회귀 방지 장치다

테스트 작성의 목적은 "지금 통과"가 아니라 "나중에도 안 깨짐"입니다.
그래서 구현 세부사항보다 외부 계약(입력/출력/오류)을 중심으로 테스트를 짜야 리팩터링 내성이 생깁니다.

또한 실패 케이스를 충분히 다루지 않으면 실제 장애는 대부분 테스트 바깥에서 발생합니다.
정상/경계/실패 3축을 항상 같이 작성하는 습관을 고정하세요.

## 아주 사소한 것까지: 용어 미니 사전

1. unit test: 작은 로직 단위 검증 테스트입니다.
2. integration test: 공개 API 사용 시나리오 테스트입니다.
3. assert_eq!: 기대값/실제값 비교 매크로입니다.
4. #[cfg(test)]: 테스트 빌드에서만 컴파일되는 블록입니다.
5. regression: 기존에 동작하던 기능이 깨지는 현상입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 테스트 전략

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 경계 케이스를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 회귀 방지에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 품질 게이트를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
