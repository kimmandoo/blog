# 02. 변수, 타입, 기초 문법

이 장은 튜토리얼 초반에서 가장 중요한 "문법 기초" 파트입니다.
변수, 타입, 제어흐름을 먼저 단단히 잡아 두면 뒤의 소유권/트레잇/동시성 학습 속도가 훨씬 빨라집니다.
많은 학습자가 프로젝트 예제를 먼저 따라가다가 여기로 되돌아오는데, 이번 시리즈에서는 이 장을 앞쪽으로 배치했습니다.
Chapter 3는 "기본 문법"처럼 보이지만, 사실 이후 모든 장의 사고방식을 결정하는 구간입니다.
특히 Rust에서는 표현식, 타입, 제어흐름이 서로 강하게 결합되어 있어서 대충 넘어가면 소유권 장에서 바로 막힙니다.

## 핵심 개념과 원리

### 1) 변수와 불변성: 기본값은 안전한 선택

Rust는 `let`으로 선언한 변수는 기본적으로 불변입니다.
즉, 값 변경이 필요할 때만 `mut`를 붙입니다.
이 규칙은 "의도하지 않은 상태 변경"을 줄여 줍니다.

```rust
let x = 10;
let mut y = 20;
y += 1;
```

변수를 늘 `mut`로 열어 두면 작성은 편하지만,
코드를 읽는 사람은 "여기서 값이 언제 바뀌는지" 계속 추적해야 합니다.

### 2) 표현식 vs 구문: Rust 코드가 수학식처럼 느껴지는 이유

Rust 블록은 값을 반환할 수 있습니다.

```rust
let number = {
    let base = 5;
    base + 1
};
```

마지막 줄에 세미콜론이 없어서 반환값이 됩니다.
세미콜론 하나가 타입을 `()`로 바꿔 버릴 수 있다는 점이 초반 핵심 포인트입니다.

### 3) 타입과 변환: 모호함을 줄이는 방향으로 설계

Rust는 강한 타입 시스템을 갖고 있어 자동 형변환이 거의 없습니다.
예를 들어 정수 + 실수 혼합 연산은 명시적 변환 없이는 불가합니다.
이 제약은 불편해 보이지만, 장기적으로는 데이터 손실/의도 불일치를 줄여 줍니다.

### 4) 제어흐름: 문법 선택이 설계 품질을 좌우한다

- `if`: 조건 분기
- `loop`: 명시적 탈출이 필요한 무한 루프
- `while`: 조건 기반 반복
- `for`: 컬렉션/범위 순회

초보자는 일단 `loop`로 시작하기 쉽지만,
가능하면 의미가 드러나는 `for`/`while`를 먼저 선택하는 습관이 좋습니다.

## 기술적인 심화 설명

### 스코프와 shadowing은 왜 유용한가?

```rust
let spaces = "   ";
let spaces = spaces.len();
```

같은 이름으로 새 변수를 만드는 shadowing은 타입 전환을 깔끔하게 표현할 수 있습니다.
Kotlin의 `val` 재할당 금지와 비슷한 장점이 있지만,
Rust shadowing은 "새 바인딩"을 만들기 때문에 타입 자체를 바꿀 수 있습니다.

### overflow 동작은 빌드 모드에 따라 다를 수 있다

정수 오버플로는 디버그 빌드에서는 panic을 유도하고,
릴리스 빌드에서는 wrapping 동작이 나타날 수 있습니다(연산 종류에 따라 다름).
그래서 수치 로직에서는 `checked_add`, `saturating_add`, `wrapping_add` 같은 의도를 명시하는 API를 고려해야 합니다.

## 대표 코드

```rust
fn classify_score(score: u32) -> &'static str {
    if score >= 90 {
        "A"
    } else if score >= 80 {
        "B"
    } else if score >= 70 {
        "C"
    } else {
        "F"
    }
}

fn main() {
    for score in [95, 82, 71, 60] {
        println!("{score} -> {}", classify_score(score));
    }
}
```

포인트:

- `if`가 표현식이므로 문자열 리터럴을 직접 반환합니다.
- 반환 타입을 `&'static str`로 고정해 의도를 분명히 했습니다.

## 실습 문제 (3단계)

### 1) 기본: 표현식 블록 체득

`let result = { ... };` 형태를 사용해,
정수 두 개의 합/차/곱 중 하나를 조건에 따라 선택 반환하는 코드를 작성하세요.

### 2) 응용: 타입 안전 점수 계산기

다음 시그니처를 구현하세요.

```rust
fn weighted_score(midterm: u32, final_exam: u32, project: u32) -> Option<u32>
```

조건:

- 각 점수는 0~100 범위
- 범위를 벗어나면 `None`
- 정상 입력이면 가중 평균(30/40/30) 반환

### 3) 도전: 작은 CLI 성적 분류기

문자열 입력을 받아 점수로 파싱하고,
`A/B/C/F`를 출력하는 함수를 모듈로 분리하세요.
파싱 실패와 범위 오류를 구분해 메시지를 다르게 출력하면 가산점입니다.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
let a = 8;
let b = 3;
let use_mul = true;

let result = {
    if use_mul { a * b } else { a + b }
};

assert_eq!(result, 24);
```

### 응용 정답 예시

```rust
fn weighted_score(midterm: u32, final_exam: u32, project: u32) -> Option<u32> {
    if midterm > 100 || final_exam > 100 || project > 100 {
        return None;
    }

    let total = midterm * 30 + final_exam * 40 + project * 30;
    Some(total / 100)
}
```

해설:

- 실패 가능성이 있으므로 반환 타입을 `Option<u32>`로 설계했습니다.
- 실수 계산 대신 정수 가중치를 사용해 부동소수 오차를 피했습니다.

### 도전 정답 방향

- `parse_score(input: &str) -> Result<u32, String>`
- `classify_score(score: u32) -> Result<&'static str, String>`

처럼 입력 단계와 도메인 규칙 단계를 분리하면 디버깅이 쉬워집니다.

## 오답 예시 3종 + 해설

### 오답 1) 세미콜론 실수로 반환 타입 붕괴

```rust
fn bad() -> i32 {
    10;
}
```

문제점: 마지막 세미콜론 때문에 `()`가 되어 컴파일 오류가 납니다.
개선: 반환할 마지막 표현식에는 세미콜론을 붙이지 않습니다.

### 오답 2) 모든 변수를 `mut`로 선언

문제점: 상태 변경 지점을 추적하기 어려워집니다.
개선: 기본은 불변, 정말 필요할 때만 `mut`를 사용합니다.

### 오답 3) 입력 검증 없이 계산 진행

문제점: 음수/범위 초과/파싱 실패가 뒤늦게 터집니다.
개선: 경계 조건을 먼저 확인하고, 실패를 타입(`Option`/`Result`)으로 노출하세요.

## 빠른 참조: 변수/타입/문법 A to Z

아래 표는 "검색 없이" 초반 학습을 진행할 수 있도록 자주 쓰는 기초 문법을 한 번에 정리한 레퍼런스입니다.

### 1) Rust 기본 스칼라 타입

- 정수: `i8`, `i16`, `i32`, `i64`, `i128`, `isize`
- 부호 없는 정수: `u8`, `u16`, `u32`, `u64`, `u128`, `usize`
- 부동소수점: `f32`, `f64`(기본)
- 불리언: `bool` (`true`/`false`)
- 문자: `char` (유니코드 스칼라 값 1개)

### 2) 복합 타입

- 튜플: `(T1, T2, ...)` 예: `(i32, f64, bool)`
- 배열: `[T; N]` 예: `[i32; 5]`
- 슬라이스: `&[T]`, 문자열 슬라이스 `&str`
- 힙 문자열: `String`

### 3) 변수 관련 키워드

- `let`: 기본 불변 바인딩
- `let mut`: 가변 바인딩
- `const`: 컴파일 타임 상수(타입 명시 필수)
- `static`: 프로그램 전체 생명주기 정적 변수
- shadowing: 같은 이름으로 새 바인딩 선언 (`let x = ...; let x = ...;`)

### 4) 숫자 리터럴 표기

- 10진수: `98_222`
- 16진수: `0xff`
- 8진수: `0o77`
- 2진수: `0b1111_0000`
- 바이트 리터럴: `b'A'`

### 5) 형변환 규칙 핵심

- Rust는 암시적 형변환을 거의 허용하지 않음
- 명시적 캐스팅: `as` (예: `x as u32`)
- 안전 변환 우선: `TryFrom`, `TryInto` 활용
- 문자열 파싱: `"42".parse::<u32>()`

### 6) 연산자/비교 연산자

- 산술: `+`, `-`, `*`, `/`, `%`
- 비교: `==`, `!=`, `>`, `<`, `>=`, `<=`
- 논리: `&&`, `||`, `!`
- 대입: `=`, `+=`, `-=`, `*=`, `/=`, `%=`

### 7) 제어흐름 한눈에 보기

- `if / else if / else`: 조건 분기
- `loop`: 명시적 `break`가 필요한 반복
- `while`: 조건 기반 반복
- `for x in iterable`: 컬렉션/범위 순회
- `match`: 완전성 보장 분기

### 8) 함수 문법 핵심

```rust
fn add(a: i32, b: i32) -> i32 {
    a + b
}
```

- 파라미터 타입 명시 필수
- 반환 타입은 `-> Type`
- 마지막 표현식(세미콜론 없음)이 반환값

### 9) 자주 헷갈리는 문법 5가지

1. `let x = 10;`과 `let x = 10` (세미콜론 누락 주의)
2. `if`는 표현식이므로 값 반환 가능
3. 배열 `[T; N]`에서 `N`은 길이, 값이 아님
4. `String`과 `&str`은 같은 타입이 아님
5. `x + y`에서 타입이 다르면 먼저 변환해야 함

## 미니 퀴즈 (정답 포함)

1) Rust 블록 마지막 줄의 세미콜론 유무가 중요한 이유는?
- 정답: 세미콜론이 있으면 구문(statement)으로 끝나 `()`가 되고, 없으면 표현식 값이 반환됩니다.

2) 모든 변수를 `mut`로 선언하지 않는 이유는?
- 정답: 상태 변경 지점을 명확히 드러내 가독성과 안정성을 높이기 위해서입니다.

3) `if`, `while`, `for`, `loop` 선택 기준은 무엇인가요?
- 정답: 분기/조건 반복/순회/명시적 탈출이 필요한 무한 루프처럼 의도에 맞는 제어문을 선택해야 합니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 변수와 타입

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 표현식 사고를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 제어흐름 선택에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 경계 조건 설계를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
