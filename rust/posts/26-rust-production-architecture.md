# 26. 프로덕션 Rust 아키텍처 가이드

이 장은 기능 구현을 넘어 서비스 운영 관점으로 Rust 프로젝트를 설계하는 방법을 다룹니다.
초보자는 "구조를 어떻게 나눠야 하는지"를 배우고, 숙련자는 "장애와 변경에 강한 설계"를 점검할 수 있습니다.

## 핵심 개념과 원리

### 1) 레이어 분리: 도메인/인프라/인터페이스

핵심 비즈니스 규칙은 프레임워크 의존을 최소화해야 테스트와 교체가 쉽습니다.

### 2) 관측성(Observability)은 기능이다

로그/메트릭/트레이싱이 없으면 장애 원인을 빠르게 찾을 수 없습니다.
운영 기능도 초기 설계에 포함해야 합니다.

### 3) 실패를 전제로 설계

타임아웃, 재시도, 서킷 브레이커, graceful shutdown은 옵션이 아니라 기본입니다.

## 기술적인 심화 설명

### 설정 관리 전략

환경 변수/설정 파일/시크릿 저장소 경계를 분리하면 배포 환경별 차이를 안전하게 관리할 수 있습니다.

### 에러 계층화

도메인 에러, 인프라 에러, API 에러를 분리해 매핑하면
내부 원인은 보존하면서 외부 응답은 일관되게 유지할 수 있습니다.

## 대표 코드

```rust
#[derive(Debug)]
enum DomainError {
    InvalidState,
    NotFound,
}

trait UserRepository {
    fn find(&self, id: u64) -> Result<String, DomainError>;
}

fn get_user_name(repo: &dyn UserRepository, id: u64) -> Result<String, DomainError> {
    repo.find(id)
}
```

## 실습 문제 (3단계)

### 1) 기본

도메인 로직과 외부 I/O 로직을 모듈로 분리하세요.

### 2) 응용

에러 타입을 2계층(도메인/인프라)으로 분리하고 API 응답으로 매핑하세요.

### 3) 도전

요청 처리 경로에 로그 + 메트릭 + 타임아웃을 모두 적용한 최소 서버를 구현하세요.

## 장 특화 실습 정답

### 기본 정답 방향

`domain/`, `infra/`, `app/` 모듈 구조를 만들고 의존 방향을 한쪽으로 고정합니다.

### 응용 정답 예시

```rust
enum AppError {
    Domain(DomainError),
    Infra(String),
}
```

### 도전 정답 핵심

핸들러 시작/종료 로그, 실패 카운터, 요청 타임아웃을 필수 항목으로 넣으면 운영 준비도가 크게 올라갑니다.

## 오답 예시 3종 + 해설

### 오답 1) 핸들러에 비즈니스 로직 집중

문제점: 테스트가 어렵고 프레임워크 교체 비용이 커집니다.
개선: 도메인 로직을 독립 모듈/서비스로 분리하세요.

### 오답 2) 에러를 문자열 하나로 통일

문제점: 원인 분류와 대응 정책 분기가 어려워집니다.
개선: 계층별 에러 타입을 유지하세요.

### 오답 3) 로깅만 하고 메트릭/트레이싱 생략

문제점: 대규모 장애에서 병목/원인 추적이 느려집니다.
개선: 최소 메트릭(요청 수, 오류율, 지연)부터 포함하세요.

## 이 장에서 꼭 가져갈 습관

1. 의존 방향을 도메인 중심으로 고정한다.
2. 관측성과 장애 대응을 기능처럼 설계한다.
3. 배포/운영 체크리스트를 코드와 함께 유지한다.

## 미니 퀴즈 (정답 포함)

1) 왜 도메인 로직을 프레임워크와 분리해야 하나요?
- 정답: 테스트와 변경(프레임워크 교체) 비용을 낮추기 위해서입니다.

2) 에러 계층화를 하는 핵심 이유는?
- 정답: 내부 원인 보존과 외부 응답 일관성을 동시에 확보하기 위해서입니다.

3) observability를 초기부터 넣어야 하는 이유는?
- 정답: 장애가 터진 뒤 추가하면 원인 추적 데이터가 이미 없는 경우가 많기 때문입니다.

## 학습 완료 기준

1. 레이어 구조를 설명하고 코드로 분리한다.
2. 계층형 에러 모델을 설계한다.
3. 최소 관측성 항목(로그/메트릭)을 적용한다.

## 실전 확장 미션

1. 기존 프로젝트에 운영 체크리스트(배포/롤백/모니터링) 문서 추가
2. 장애 시나리오 3개를 정해 대응 런북(runbook) 작성

## 부가 설명: 왜 이 장이 "숙련자 분기점"인가

초중급은 기능 구현으로도 성과를 낼 수 있지만, 숙련자는 장애/변경/운영 비용까지 설계합니다.
서비스가 커질수록 코드 품질보다 운영 구조 품질이 더 큰 차이를 만듭니다.

Rust는 타입 안전성 덕분에 구현 안정성이 높지만,
아키텍처와 관측성을 잘못 설계하면 여전히 운영 실패는 발생합니다.

## 아주 사소한 것까지: 용어 미니 사전

1. observability: 시스템 내부 상태를 외부 신호로 파악할 수 있는 능력입니다.
2. SLO: 서비스 목표 지표(가용성/지연 등)입니다.
3. runbook: 장애 대응 절차 문서입니다.
4. circuit breaker: 실패가 연쇄 확산되는 것을 막는 보호 패턴입니다.
5. dependency direction: 모듈 간 의존이 흐르는 방향 규칙입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 운영 아키텍처

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 관측성를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 장애 대응에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 배포/롤백 전략를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
