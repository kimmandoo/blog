# 01. 설치와 개발환경 세팅

Rust를 배우기 시작할 때 가장 먼저 해야 할 일은 문법 암기가 아니라 개발환경을 "재현 가능하게" 만드는 일입니다.
오늘은 단순히 `Hello, world!`를 찍는 데서 끝내지 않고, 왜 `rustup`과 `cargo`가 Rust 학습의 핵심 도구인지 원리부터 정리합니다.

## 핵심 개념과 원리

### 1) Rust 설치는 "컴파일러 하나 설치"가 아니라 toolchain 관리다

Rust는 `rustc`만 있으면 돌아가지만, 실무와 학습에서는 버전 관리가 더 중요합니다.
`rustup`은 다음을 관리합니다.

- Rust 버전(stable/beta/nightly)
- 타깃(예: `x86_64-unknown-linux-gnu`, `wasm32-unknown-unknown`)
- 보조 도구(`rustfmt`, `clippy`, `rust-analyzer` 지원 도구 등)

같은 저장소를 팀원이 각자 다른 버전으로 빌드하면 "내 컴퓨터에서는 되는데요" 문제가 생깁니다.
그래서 Rust 학습 초기부터 버전을 고정하고, 어떤 도구를 쓰는지 문서화하는 습관이 중요합니다.

### 2) Cargo는 빌드 도구 + 패키지 관리자 + 작업 자동화 도구

`cargo`는 단순 실행기가 아닙니다.

- `cargo new`: 프로젝트 뼈대 생성
- `cargo check`: 실행 파일 생성 없이 타입/컴파일 오류 빠르게 확인
- `cargo run`: 빌드 후 실행
- `cargo test`: 테스트 실행
- `cargo build --release`: 최적화 빌드

초보자가 가장 먼저 익혀야 하는 루프는 `check -> fix -> run -> test`입니다.
특히 `cargo check`를 자주 쓰면 피드백 속도가 매우 빨라집니다.

### 3) Rust 프로젝트 구조는 의도를 표현하는 계약이다

기본 구조:

- `Cargo.toml`: 패키지 메타데이터, 의존성, 에디션
- `src/main.rs`: 바이너리 엔트리 포인트
- `src/lib.rs`: 라이브러리 코드(재사용/테스트 중심)

학습 단계에서도 "실행 코드"와 "검증 가능한 로직"을 분리해 두면, 나중에 테스트 작성이 훨씬 쉬워집니다.

## 기술적인 심화 설명

### Rustup 채널(stable/beta/nightly)을 어떻게 써야 하나?

- 기본 학습: `stable`
- 최신 기능 사전 검증: `beta`
- 실험적 기능(unstable) 실습: `nightly`

초보 단계에서는 `stable`만 써도 충분합니다.
`nightly`를 조기에 쓰면 문법보다 도구 변동에 흔들리기 쉽습니다.

### Kotlin과 비교해 보면 무엇이 다른가?

Kotlin도 Gradle/Maven으로 빌드 자동화가 되지만, Rust는 `cargo` 단일 진입점이 매우 강력합니다.
즉, 빌드/테스트/문서/벤치마크 루틴을 한 도구 체계 안에서 익히기 쉽습니다.

또한 Rust는 컴파일 단계에서 메모리 안전성과 소유권 규칙을 강제하기 때문에,
프로젝트 초반부터 "코드가 왜 거부되는지"를 읽는 능력이 중요합니다.
이 감각이 쌓이면 런타임 버그를 사전에 줄일 수 있습니다.

## 대표 코드

아래 코드는 Chapter 1 수준에서 가장 먼저 익혀야 할 `cargo` 기반 최소 구조입니다.

```rust
fn main() {
    let language = "Rust";
    println!("Hello, {language}!");
}
```

겉으로는 단순하지만, 이미 중요한 규칙이 있습니다.

- `println!`은 함수가 아니라 매크로(`!`)입니다.
- `language`는 기본적으로 불변 바인딩입니다.
- 포맷 문자열 문법은 컴파일 시점에 검증됩니다.

## 실습 문제 (3단계)

### 1) 기본: 도구 루틴 만들기

1. `cargo new hello_rust`로 프로젝트를 만듭니다.
2. `src/main.rs`에서 출력 문구를 2번 바꿉니다.
3. 매번 `cargo check` 후 `cargo run`을 실행하고 차이를 기록합니다.

목표: "코드 수정 -> check -> run" 루프를 몸에 익히기.

### 2) 응용: 간단한 함수 분리

`main`에서 모든 출력을 처리하지 말고 `fn greeting(name: &str) -> String` 함수를 만들어 호출하세요.
`main`은 입출력 조립만 담당하게 바꾸고, 문자열 생성 로직은 함수로 분리합니다.

목표: 역할 분리와 시그니처 감각 익히기.

### 3) 도전: 테스트 가능한 구조 만들기

`src/lib.rs`를 만들고 `greeting`을 옮긴 뒤, 단위 테스트를 2개 작성하세요.

- 정상 입력("Rust")
- 경계 입력(빈 문자열)

목표: 실행 코드(`main`)와 검증 코드(`lib`) 분리.

## 장 특화 실습 정답

### 기본 정답 예시

```bash
cargo new hello_rust
cd hello_rust
cargo check
cargo run
```

```rust
fn main() {
    println!("Hello, Rust learner!");
}
```

### 응용 정답 예시

```rust
fn greeting(name: &str) -> String {
    if name.trim().is_empty() {
        "Hello, anonymous learner!".to_string()
    } else {
        format!("Hello, {name}!")
    }
}

fn main() {
    println!("{}", greeting("Rust"));
}
```

해설:

- `trim().is_empty()`로 공백 입력을 경계 처리했습니다.
- `String`을 반환해 출력 정책과 메시지 생성 책임을 분리했습니다.

### 도전 정답 예시

```rust
pub fn greeting(name: &str) -> String {
    if name.trim().is_empty() {
        "Hello, anonymous learner!".to_string()
    } else {
        format!("Hello, {name}!")
    }
}

#[cfg(test)]
mod tests {
    use super::greeting;

    #[test]
    fn greeting_with_name() {
        assert_eq!(greeting("Rust"), "Hello, Rust!");
    }

    #[test]
    fn greeting_with_empty_input() {
        assert_eq!(greeting("   "), "Hello, anonymous learner!");
    }
}
```

## 오답 예시 3종 + 해설

### 오답 1) `cargo run`만 반복하고 `cargo check`를 안 쓰는 경우

문제점: 작은 수정에서도 실행 파일 빌드까지 매번 수행해 피드백이 느려집니다.
개선: 개발 중에는 `cargo check`를 기본 루프로 두고, 동작 확인이 필요할 때만 `cargo run`을 사용합니다.

### 오답 2) `main`에 모든 로직을 몰아넣는 경우

```rust
fn main() {
    let name = "Rust";
    if name.trim().is_empty() {
        println!("Hello, anonymous learner!");
    } else {
        println!("Hello, {name}!");
    }
    // 이후 로직도 전부 계속 추가...
}
```

문제점: 테스트가 어렵고 변경 시 영향 범위가 커집니다.
개선: 순수 로직은 함수/`lib.rs`로 분리하고 `main`은 조립 계층으로 유지합니다.

### 오답 3) 버전 관리 없이 로컬 환경에만 의존하는 경우

문제점: 팀/CI 환경에서 동일한 결과를 재현하기 어렵습니다.
개선: `rustup show`, `rustc --version`, `cargo --version` 결과를 문서화하고, 필요하면 `rust-toolchain.toml`로 버전 고정합니다.

## 이 장에서 꼭 가져갈 습관

1. 매일 `check -> run -> test` 루프를 반복한다.
2. `main`은 얇게, 핵심 로직은 분리한다.
3. 도구 버전을 명시해 재현 가능한 학습 환경을 만든다.

## 미니 퀴즈 (정답 포함)

1) `cargo check`와 `cargo run`의 가장 큰 차이는 무엇인가요?
- 정답: `cargo check`는 실행 파일 생성 없이 컴파일 오류를 빠르게 확인하고, `cargo run`은 빌드 후 실행까지 수행합니다.

2) 학습 초반에 `stable` 채널을 기본으로 권장하는 이유는 무엇인가요?
- 정답: 문법/개념 학습에 집중하기 좋고 도구 변화로 인한 불필요한 흔들림을 줄일 수 있기 때문입니다.

3) `main.rs`와 `lib.rs`를 분리하면 얻는 이점은 무엇인가요?
- 정답: 실행 조립 계층과 핵심 로직을 분리해 테스트와 재사용이 쉬워집니다.

## 학습 완료 기준

1. `rustup show` 출력으로 toolchain 상태를 설명할 수 있다.
2. `cargo check -> run -> test` 루프를 스스로 적용한다.
3. `main`/`lib` 분리 이유를 말하고 작은 예제로 구현한다.

## 실전 확장 미션

1. `rust-toolchain.toml`을 추가해 버전을 고정해 보기
2. CI에서 `cargo check`를 첫 단계로 두는 워크플로 만들기

## 부가 설명: 환경 세팅에서 가장 자주 막히는 지점

초보자는 설치가 끝나면 바로 코드로 넘어가지만, 실제로는 버전 불일치가 가장 많은 시간을 잡아먹습니다.
그래서 첫 주에는 기능 개발보다 `rustup show`, `cargo --version`, `rustc --version` 확인을 습관화하는 편이 더 효율적입니다.

또 하나는 IDE 설정입니다. 자동 포맷(`rustfmt`)과 진단(`clippy`)이 바로 보이게 만들어 두면,
문법 실수와 스타일 편차를 초반에 자동으로 교정할 수 있어 학습 피로가 줄어듭니다.

## 아주 사소한 것까지: 용어 미니 사전

1. toolchain: 컴파일러/표준 라이브러리/도구 묶음입니다.
2. stable/beta/nightly: Rust 릴리스 채널 3종입니다.
3. cargo check: 실행 파일 생성 없이 컴파일 오류를 확인합니다.
4. cargo run: 빌드 후 실행까지 수행합니다.
5. Cargo.toml: 패키지 메타데이터/의존성/설정을 담는 파일입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 도구체인 재현성

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 버전 고정 정책를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 개발 루프 자동화에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 팀 온보딩를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
