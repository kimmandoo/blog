# 15. 스마트 포인터 심화

스마트 포인터 장은 "문법"보다 "소유권 모델 선택"이 핵심입니다.
어떤 포인터를 쓰느냐에 따라 성능, 동시성 가능성, 디버깅 난이도가 크게 달라집니다.

## 핵심 개념과 원리

### 1) `Box<T>`: 단일 소유 + 힙 할당

재귀 타입이나 큰 데이터 이동 비용을 줄일 때 유용합니다.
소유자는 하나이며, 컴파일 타임 빌림 규칙을 그대로 따릅니다.

### 2) `Rc<T>`: 단일 스레드 공유 소유

읽기 중심 그래프 구조에서 여러 소유자가 필요할 때 사용합니다.
참조 카운트로 수명을 관리하지만, 스레드 안전하지 않습니다.

### 3) `RefCell<T>`: 내부 가변성

컴파일 타임 대신 런타임에 빌림 규칙을 검사합니다.
유연하지만 규칙 위반 시 panic 가능성이 있으므로 범위를 최소화해야 합니다.

## 기술적인 심화 설명

### `Rc<RefCell<T>>` 조합은 왜 자주 나오나?

공유 소유 + 변경 가능 상태가 동시에 필요할 때 많이 쓰입니다.
다만 복잡도가 빠르게 증가하므로, 먼저 데이터 흐름 재설계를 검토하는 게 좋습니다.

### `Drop` 구현 시 주의점

`Drop`은 자원 정리 훅입니다.
여기서 panic이 나면 이중 패닉 위험이 있으므로 가벼운 정리만 수행하세요.

### `Deref`가 만드는 API 경험

`Deref`를 구현하면 스마트 포인터가 일반 참조처럼 동작합니다.
하지만 과도한 자동 변환은 코드 읽기를 어렵게 만들 수 있어 명확성이 우선입니다.

## 대표 코드

```rust
use std::cell::RefCell;
use std::rc::Rc;

#[derive(Debug)]
struct Counter {
    value: RefCell<i32>,
}

fn main() {
    let counter = Rc::new(Counter { value: RefCell::new(0) });
    *counter.value.borrow_mut() += 1;
    println!("{:?}", counter);
}
```

## 실습 문제 (3단계)

### 1) 기본

재귀 리스트 타입을 `Box`로 구현하고 길이를 구하는 함수 작성.

### 2) 응용

`Rc`를 사용해 하나의 설정 객체를 두 모듈에서 공유 읽기.

### 3) 도전

`Rc<RefCell<Vec<String>>>` 기반 로그 버퍼를 만들고,
여러 컴포넌트가 append하는 구조를 구현.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
enum List {
    Cons(i32, Box<List>),
    Nil,
}
```

### 응용 정답 예시

```rust
use std::rc::Rc;

#[derive(Debug)]
struct Config {
    host: String,
}

let cfg = Rc::new(Config { host: "localhost".to_string() });
let a = Rc::clone(&cfg);
let b = Rc::clone(&cfg);
```

### 도전 정답 예시

```rust
use std::cell::RefCell;
use std::rc::Rc;

type SharedLog = Rc<RefCell<Vec<String>>>;

fn push_log(log: &SharedLog, msg: &str) {
    log.borrow_mut().push(msg.to_string());
}
```

## 오답 예시 3종 + 해설

### 오답 1) 공유가 필요한데 `Box`만 사용

문제점: 소유자 하나만 허용되어 구조 확장이 막힙니다.
개선: 공유 소유가 필요하면 `Rc`/`Arc`를 고려하세요.

### 오답 2) `RefCell` 빌림 범위를 길게 유지

문제점: 중복 빌림으로 런타임 panic 위험이 커집니다.
개선: `borrow_mut()` 결과의 생존 범위를 짧게 끝내세요.

### 오답 3) 단일 스레드인데 습관적으로 `Arc<Mutex<T>>`

문제점: 불필요한 동기화 비용과 복잡성이 증가합니다.
개선: 스레드 모델에 맞는 최소 도구를 선택하세요.

## 미니 퀴즈 (정답 포함)

1) `Box<T>`와 `Rc<T>`의 핵심 차이는?
- 정답: `Box`는 단일 소유, `Rc`는 단일 스레드 다중 소유를 지원합니다.

2) `RefCell<T>`를 사용할 때 가장 조심할 점은?
- 정답: 빌림 규칙을 런타임에 검사하므로 중복 가변 빌림 시 panic 가능성이 있습니다.

3) 단일 스레드 코드에서 `Arc<Mutex<T>>` 남용이 안 좋은 이유는?
- 정답: 불필요한 동기화 비용과 복잡성만 증가하기 때문입니다.

## 부가 설명: 스마트 포인터 선택 실수를 줄이는 질문

포인터를 고를 때는 먼저 "공유가 필요한가", "변경이 필요한가", "스레드를 넘나드나"를 순서대로 확인하세요.
이 세 질문만으로도 `Box/Rc/RefCell/Arc/Mutex` 후보가 빠르게 좁혀집니다.

또한 `RefCell`은 편해서 쓰는 도구가 아니라 설계 타협 도구입니다.
사용했다면 왜 컴파일 타임 검증을 런타임 검증으로 바꿨는지 주석/문서로 근거를 남기세요.

## 아주 사소한 것까지: 용어 미니 사전

1. Box<T>: 단일 소유 힙 포인터입니다.
2. Rc<T>: 단일 스레드 공유 소유 포인터입니다.
3. Arc<T>: 멀티스레드 공유 소유 포인터입니다.
4. RefCell<T>: 런타임 빌림 검사 내부 가변성 도구입니다.
5. Deref/Drop: 역참조 동작/소멸 시 동작을 정의하는 트레잇입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 포인터 선택 기준

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 내부 가변성를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 공유 소유에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 런타임 비용를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
