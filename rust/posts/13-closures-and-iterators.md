# 13. 클로저와 이터레이터

클로저와 이터레이터는 Rust에서 함수형 스타일을 실제 성능과 연결해 주는 도구입니다.
Chapter 13의 포인트는 문법 암기가 아니라 "소유권 규칙 안에서 선언적 코드를 쓰는 법"입니다.

## 핵심 개념과 원리

### 1) 클로저 캡처 방식

클로저는 주변 변수를 `&T`, `&mut T`, `T` 중 필요한 방식으로 캡처합니다.
그래서 같은 코드라도 클로저 본문이 바뀌면 캡처 방식이 바뀔 수 있습니다.

### 2) 이터레이터는 지연 평가(lazy)

`map`, `filter`를 호출해도 바로 실행되지 않습니다.
`collect`, `for_each`, `sum` 같은 소비자가 있어야 실제 계산이 일어납니다.

### 3) 선언적 체인은 의도를 단계로 드러낸다

`filter -> map -> collect` 순서를 보면
데이터가 어떻게 변환되는지 한눈에 보입니다.

## 기술적인 심화 설명

### `iter`, `iter_mut`, `into_iter` 차이

- `iter`: 불변 참조 순회
- `iter_mut`: 가변 참조 순회
- `into_iter`: 소유권 이동

선택이 곧 소유권 설계입니다.

### 클로저 trait (`Fn`, `FnMut`, `FnOnce`)

Rust는 클로저 사용 패턴에 따라 호출 가능 trait를 다르게 요구합니다.
한 번만 소비하는 클로저가 필요한지, 반복 호출 가능한지 API 설계 시 명확히 해야 합니다.

## 대표 코드

```rust
fn expensive_filter(nums: &[i32], threshold: i32) -> Vec<i32> {
    nums.iter()
        .copied()
        .filter(|n| *n >= threshold)
        .map(|n| n * 2)
        .collect()
}
```

## 실습 문제 (3단계)

### 1) 기본

숫자 벡터에서 짝수만 골라 제곱한 벡터를 반환하는 함수 작성.

### 2) 응용

문장 배열에서 길이 5 이상 문자열만 소문자로 변환해 반환.

### 3) 도전

이전 계산 결과를 캐싱하는 클로저 기반 계산기(메모이제이션) 구현.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
fn even_squares(input: &[i32]) -> Vec<i32> {
    input.iter().copied().filter(|n| n % 2 == 0).map(|n| n * n).collect()
}
```

### 응용 정답 예시

```rust
fn normalize_words(words: &[&str]) -> Vec<String> {
    words
        .iter()
        .filter(|w| w.len() >= 5)
        .map(|w| w.to_lowercase())
        .collect()
}
```

### 도전 정답 방향

`HashMap`을 캡처한 클로저를 만들고, 동일 입력이면 저장값을 반환하도록 설계합니다.

## 오답 예시 3종 + 해설

### 오답 1) 이터레이터 체인 중간에 불필요한 `collect`

문제점: 중간 할당이 늘어 성능과 가독성이 함께 나빠집니다.
개선: 마지막 소비 시점까지 체인을 유지하세요.

### 오답 2) 캡처 move를 의식하지 않고 원본 재사용

문제점: 클로저에 소유권이 이동해 이후 원본 접근이 막힙니다.
개선: 참조 캡처 또는 clone 필요성을 먼저 판단하세요.

### 오답 3) 긴 체인을 한 줄로 과도하게 작성

문제점: 디버깅과 리뷰가 어려워집니다.
개선: 의미 단위로 중간 변수/함수를 도입하세요.

## 미니 퀴즈 (정답 포함)

1) 이터레이터 체인이 즉시 실행되지 않는 이유는?
- 정답: Rust 이터레이터는 지연 평가이므로 `collect`, `sum` 같은 소비자가 있어야 실행됩니다.

2) `iter` / `iter_mut` / `into_iter` 차이가 중요한 이유는?
- 정답: 참조/가변 참조/소유권 이동을 구분해 데이터 소유 모델을 정확히 제어하기 위해서입니다.

3) 긴 체인을 중간 변수로 나누는 실무적 이유는?
- 정답: 디버깅과 코드 리뷰 가독성을 높이고 의미 단위를 분명하게 만들 수 있습니다.

2. iterator 지연 평가와 소비 시점을 구분한다.
3. 체인을 읽기 쉬운 단계로 분해한다.

## 실전 확장 미션

1. 메모이제이션 클로저 구현
2. iterator 성능 프로파일 비교

## 부가 설명: 함수형 스타일을 Rust답게 쓰는 기준

체인이 짧다고 좋은 코드가 되는 것은 아닙니다.
클로저 캡처 방식과 소유권 이동이 읽는 사람에게 분명히 보이도록 작성해야 유지보수가 쉬워집니다.

성능이 걱정된다면 감으로 최적화하지 말고, 중간 할당 여부와 소비 시점을 먼저 점검하세요.
대부분의 경우 구조를 명확히 하는 리팩터링이 성능과 가독성을 함께 개선합니다.

## 아주 사소한 것까지: 용어 미니 사전

1. closure: 주변 환경을 캡처하는 익명 함수입니다.
2. iterator: 순회 추상화 인터페이스입니다.
3. lazy evaluation: 소비 시점까지 계산을 미루는 방식입니다.
4. collect: 이터레이터를 컬렉션으로 모읍니다.
5. Fn/FnMut/FnOnce: 클로저 호출 가능성 제약 트레잇입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 지연 평가

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 캡처 규칙를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 체인 가독성에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 할당 최적화를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
