# 17. Rust에서 객체지향 설계하기

Rust는 전통적 클래스 상속 OOP와 다르지만,
캡슐화/추상화/다형성은 더 명확하게 구현할 수 있습니다.
Chapter 17은 "상속 없이도 유연한 설계"를 익히는 장입니다.

## 핵심 개념과 원리

### 1) 캡슐화: 필드는 숨기고 메서드로 통제

`pub`를 최소화하면 내부 상태 변경 규칙을 한곳에서 관리할 수 있습니다.

### 2) 다형성: 트레잇 객체

`Vec<Box<dyn Draw>>`처럼 서로 다른 타입을 같은 인터페이스로 다룰 수 있습니다.
런타임 다형성이 필요할 때 유용합니다.

### 3) 상태 패턴

상태 전이 규칙을 호출자 if-else가 아니라 상태 객체로 옮기면
복잡한 분기 로직이 안정화됩니다.

## 기술적인 심화 설명

### 제네릭 vs 트레잇 객체 선택

- 제네릭: 정적 디스패치, 성능 유리, 타입 고정
- 트레잇 객체: 동적 디스패치, 유연성 유리, 런타임 다형성

요구사항에 따라 선택해야 하며, 무조건 하나가 정답은 아닙니다.

### 상속 대신 합성

Rust는 상속보다 "작은 타입 + 트레잇 조합"을 선호합니다.
변경 단위를 작게 유지해 테스트와 리팩터링이 쉬워집니다.

## 대표 코드

```rust
trait Draw {
    fn draw(&self);
}

struct Button;
impl Draw for Button {
    fn draw(&self) {
        println!("draw button");
    }
}

fn render_all(components: &[Box<dyn Draw>]) {
    for c in components {
        c.draw();
    }
}
```

## 실습 문제 (3단계)

### 1) 기본

`Draw` 트레잇을 구현하는 `Text`, `Checkbox` 타입 추가.

### 2) 응용

`Post` 상태를 `Draft -> Review -> Published`로 전이하는 상태 패턴 구현.

### 3) 도전

상태 전이에 권한 규칙(작성자/리뷰어)을 추가하고 오류를 `Result`로 반환.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
struct Text;
impl Draw for Text {
    fn draw(&self) { println!("draw text"); }
}
```

### 응용 정답 방향

`enum` 기반 상태 모델로 먼저 구현한 뒤,
트레잇 객체 상태 패턴으로 확장하면 이해가 쉽습니다.

### 도전 정답 핵심

`request_review(user)`와 `approve(user)`에서 권한 검증 실패를 `Err`로 반환해 상태 무결성을 유지합니다.

## 오답 예시 3종 + 해설

### 오답 1) 다형성이 필요한데 거대한 match 유지

문제점: 타입 추가 시 분기 수정이 폭증합니다.
개선: 공통 행동은 트레잇으로 이동하세요.

### 오답 2) 모든 상태 전이를 호출자가 직접 관리

문제점: 상태 규칙이 곳곳에 분산되어 버그가 증가합니다.
개선: 상태 전이 책임을 타입 내부로 모으세요.

### 오답 3) 트레잇 객체 남용

문제점: 단순한 정적 구조에서도 동적 디스패치 비용/복잡도만 늘어납니다.
개선: 런타임 다형성이 진짜 필요한 경계에서만 사용하세요.

## 미니 퀴즈 (정답 포함)

1) Rust에서 상속 대신 합성을 선호하는 이유는?
- 정답: 책임을 작은 단위로 분리해 변경/테스트 비용을 낮출 수 있기 때문입니다.

2) 트레잇 객체를 써야 하는 상황은?
- 정답: 서로 다른 타입을 런타임에 같은 인터페이스로 다뤄야 할 때입니다.

3) 상태 패턴의 핵심 이점은?
- 정답: 상태 전이 규칙을 타입 내부로 모아 호출자 분기 복잡도를 줄이는 것입니다.

## 학습 완료 기준

1. 상속 대신 합성+트레잇으로 다형성을 구현한다.
2. 트레잇 객체와 제네릭 선택 기준을 설명한다.
3. 상태 패턴으로 전이 규칙을 캡슐화한다.

## 실전 확장 미션

1. UI 컴포넌트 렌더러 확장
2. 상태 전이 권한 정책 추가

## 부가 설명: Rust식 OOP의 핵심은 조합 가능성

Rust에서 다형성은 상속 계층보다 "작은 계약(트레잇)" 조합으로 만드는 편이 더 강력합니다.
타입이 늘어날수록 이 방식이 테스트와 변경에 훨씬 유리하다는 점이 드러납니다.

트레잇 객체와 제네릭은 대체 관계가 아니라 목적이 다른 도구입니다.
런타임 유연성이 필요한 경계인지, 컴파일 타임 최적화가 중요한 경계인지 먼저 판단하세요.

## 아주 사소한 것까지: 용어 미니 사전

1. trait object: 런타임 다형성을 위한 동적 디스패치 타입입니다.
2. dynamic dispatch: 실행 시점에 호출 대상을 결정합니다.
3. state pattern: 상태별 동작을 타입/객체로 분리하는 패턴입니다.
4. composition: 상속 대신 조합으로 기능을 구성하는 방식입니다.
5. encapsulation: 내부 상태를 숨기고 인터페이스로 통제합니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 합성 중심 설계

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 다형성 경계를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 상태 패턴에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 확장성 유지를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
