# 14. Cargo 고급 기능과 crates.io

Chapter 14는 "코드"보다 "배포 가능한 프로젝트 운영"에 초점을 둡니다.
Cargo를 제대로 쓰면 개발-테스트-문서-배포 루프가 표준화됩니다.

## 핵심 개념과 원리

### 1) 빌드 프로필은 성능과 디버깅의 스위치

`dev`는 빠른 컴파일과 디버깅 친화,
`release`는 실행 성능 최적화 중심입니다.
학습 중 벤치마크 결과를 볼 때는 반드시 release를 사용해야 합니다.

### 2) 워크스페이스는 다중 크레이트 운영 기본

라이브러리, CLI, 내부 툴을 한 저장소에서 관리할 때
워크스페이스를 쓰면 의존성/빌드 캐시/명령 실행을 통합할 수 있습니다.

### 3) crates.io 배포는 계약 공개

패키지를 공개하면 API와 문서가 외부 계약이 됩니다.
버전 관리(semantic versioning)와 README/docs 품질이 곧 신뢰입니다.

## 기술적인 심화 설명

### `cargo doc` 문화

Rust 생태계는 문서 자동 생성이 강력합니다.
pub API에는 예제를 포함한 doc comment를 붙이는 습관이 중요합니다.

### `cargo publish --dry-run`

실제 배포 전에 패키징 결과를 검증하는 안전장치입니다.
누락 파일, 잘못된 메타데이터를 조기에 잡을 수 있습니다.

### Kotlin/Gradle 대비 장점

Gradle은 유연하지만 복잡해질 수 있습니다.
Cargo는 관례가 강해서 팀 전체 빌드 루틴을 빠르게 통일하기 좋습니다.

## 대표 코드

```toml
[package]
name = "my_lib"
version = "0.1.0"
edition = "2024"
description = "utility crate"
license = "MIT"

[dependencies]
```

```bash
cargo test
cargo doc --open
cargo publish --dry-run
```

## 실습 문제 (3단계)

### 1) 기본

현재 프로젝트에 `cargo doc --open`을 실행하고,
문서에 표시되는 pub API를 확인하세요.

### 2) 응용

간단한 workspace(`core`, `cli`)를 구성하고,
루트에서 `cargo test --workspace`를 실행하세요.

### 3) 도전

배포 전 체크리스트를 만들고,
`fmt`, `clippy`, `test`, `doc`, `publish --dry-run`을 순서대로 자동화하세요.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
/// 두 수의 합을 반환합니다.
///
/// # Examples
///
/// ```
/// assert_eq!(my_lib::add(2, 3), 5);
/// ```
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
```

### 응용 정답 예시

```toml
# Cargo.toml (workspace root)
[workspace]
members = ["core", "cli"]
resolver = "2"
```

### 도전 정답 방향

CI 스크립트에 아래 순서를 고정합니다.

1. `cargo fmt -- --check`
2. `cargo clippy -- -D warnings`
3. `cargo test --workspace`
4. `cargo doc --no-deps`
5. `cargo publish --dry-run`

## 오답 예시 3종 + 해설

### 오답 1) release 검증 없이 성능 결론 내리기

문제점: dev 빌드 결과로 성능 판단하면 왜곡됩니다.
개선: 성능 평가는 release 기준으로만 진행하세요.

### 오답 2) 문서/라이선스 없이 배포 시도

문제점: 사용자 신뢰와 패키지 품질이 떨어집니다.
개선: README, license, description, examples를 기본 세트로 준비하세요.

### 오답 3) 배포 전에 dry-run 생략

문제점: 사소한 메타데이터 실수로 배포 실패가 발생합니다.
개선: `publish --dry-run`을 필수 게이트로 넣으세요.

## 미니 퀴즈 (정답 포함)

1) 성능 측정 시 `dev` 대신 `release`를 봐야 하는 이유는?
- 정답: 최적화 수준이 달라 실행 성능 수치가 크게 달라지기 때문입니다.

2) `cargo publish --dry-run`이 중요한 이유는?
- 정답: 실제 배포 전 패키징/메타데이터 오류를 안전하게 검증할 수 있기 때문입니다.

3) 워크스페이스의 실무 장점은?
- 정답: 다중 크레이트를 공통 명령/캐시/의존성 정책으로 일관되게 관리할 수 있습니다.

## 학습 완료 기준

1. dev/release 프로필 차이를 실험으로 설명한다.
2. workspace 명령을 일관되게 적용한다.
3. 배포 전 dry-run 검증 루틴을 수행한다.

## 실전 확장 미션

1. 배포 체크 스크립트 작성
2. crate 문서 예제(doctest) 3개 추가

## 부가 설명: 배포 품질은 코드 밖에서 결정된다

많은 학습자가 코드 완성만 보고 끝내지만, 실제 품질은 배포 루틴에서 갈립니다.
문서, 버전, 라이선스, dry-run, CI 순서가 고정돼야 재현 가능한 릴리스를 만들 수 있습니다.

특히 워크스페이스 운영에서는 명령 통일이 중요합니다.
팀원마다 다른 실행 습관을 쓰기 시작하면 같은 저장소에서도 결과가 달라질 수 있습니다.

## 아주 사소한 것까지: 용어 미니 사전

1. workspace: 여러 크레이트를 묶어 관리하는 단위입니다.
2. profile: dev/release 빌드 설정 세트입니다.
3. doctest: 문서 코드 블록을 테스트로 실행합니다.
4. publish --dry-run: 실제 배포 전 검증 명령입니다.
5. semver: 버전 호환성 규칙(major/minor/patch)입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 배포 준비도

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 워크스페이스 운영를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 문서/버전 관리에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 릴리스 신뢰성를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
