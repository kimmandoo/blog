# 12. 미니그렙 프로젝트 완성

미니그렙 프로젝트는 지금까지 배운 문법을 "실행 가능한 프로그램"으로 묶는 첫 관문입니다.
핵심은 grep 기능 그 자체보다, `main`/`lib` 분리와 에러 흐름 설계를 익히는 데 있습니다.

## 핵심 개념과 원리

### 1) 요구사항을 먼저 타입으로 옮긴다

검색어, 파일 경로, 대소문자 옵션을 `Config`에 담으면
실행 로직이 단순해지고 테스트가 쉬워집니다.

### 2) `main`은 조립, `run`은 로직

- `main`: 인자 파싱, 오류 출력, 종료 코드
- `run`: 파일 읽기, 라인 필터링, 결과 출력

이 분리를 지키면 CLI가 커져도 구조가 유지됩니다.

### 3) 검색 함수는 순수하게 유지

`search(query, contents) -> Vec<&str>` 같은 함수는
입력과 출력만 다루므로 단위 테스트가 매우 쉽습니다.

## 기술적인 심화 설명

### 환경 변수 처리 지점

대소문자 무시 옵션(`IGNORE_CASE`)을 어디서 읽을지 결정해야 합니다.
보통 `Config::build`에서 읽어 한 번만 결정하면,
나머지 로직은 순수하게 유지됩니다.

### 메모리 vs 스트리밍

Book 예제는 `read_to_string`으로 파일 전체를 메모리에 올립니다.
작은 파일엔 충분하지만, 대용량 로그엔 `BufRead` 스트리밍이 유리합니다.
이번 장에서는 구조를 먼저 익히고, 이후 최적화를 붙이면 됩니다.

### Kotlin CLI와 비교

Kotlin도 CLI를 만들 수 있지만,
Rust는 `Result` 기반 실패 전파와 단일 바이너리 배포가 강점입니다.
운영 환경 배포까지 염두에 두면 Rust CLI의 장점이 더 커집니다.

## 대표 코드

```rust
pub struct Config {
    pub query: String,
    pub file_path: String,
    pub ignore_case: bool,
}

pub fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {
    contents
        .lines()
        .filter(|line| line.contains(query))
        .collect()
}
```

## 실습 문제 (3단계)

### 1) 기본: `Config::build` 구현

커맨드라인 인자에서 query/file_path를 읽고,
인자가 부족하면 `Err`를 반환하세요.

### 2) 응용: 대소문자 무시 검색

`search_case_insensitive` 함수를 추가하고,
`ignore_case` 옵션에 따라 검색 함수를 분기하세요.

### 3) 도전: 라인 번호 출력

검색 결과를 출력할 때 `line_number:content` 형식으로 출력하세요.

## 장 특화 실습 정답

### 기본 정답 예시

```rust
impl Config {
    pub fn build(args: &[String]) -> Result<Config, String> {
        if args.len() < 3 {
            return Err("usage: minigrep <query> <file_path>".to_string());
        }
        Ok(Config {
            query: args[1].clone(),
            file_path: args[2].clone(),
            ignore_case: std::env::var("IGNORE_CASE").is_ok(),
        })
    }
}
```

### 응용 정답 예시

```rust
pub fn search_case_insensitive<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {
    let query = query.to_lowercase();
    contents
        .lines()
        .filter(|line| line.to_lowercase().contains(&query))
        .collect()
}
```

### 도전 정답 예시

```rust
for (idx, line) in contents.lines().enumerate() {
    if line.contains(&config.query) {
        println!("{}:{}", idx + 1, line);
    }
}
```

## 오답 예시 3종 + 해설

### 오답 1) `main`에 모든 로직 집중

문제점: 테스트가 거의 불가능해지고 변경 비용이 급증합니다.
개선: 파싱/실행/검색 함수를 분리하세요.

### 오답 2) 인자 부족 시 `panic!`

문제점: CLI 사용자가 잘못된 입력을 했는데 앱이 과격하게 종료됩니다.
개선: 사용법 메시지와 함께 `Err`를 반환하세요.

### 오답 3) 검색 함수에서 직접 출력까지 수행

문제점: 로직과 I/O가 결합되어 재사용/테스트가 어려워집니다.
개선: 검색 함수는 결과만 반환하고 출력은 호출자 계층에서 담당하세요.

## 이 장에서 꼭 가져갈 습관

1. 프로젝트는 `main`/`lib` 책임 분리로 시작한다.
2. 실패는 `Result`로 상위에 전파한다.
3. 핵심 검색 로직은 순수 함수로 만든다.

## 미니 퀴즈 (정답 포함)

1) `main`과 `run`을 분리하는 구조적 이점은?
- 정답: `main`은 입출력 조립에 집중하고 핵심 로직은 테스트 가능한 함수로 분리할 수 있습니다.

2) `Config` 구조체를 두는 이유는?
- 정답: 인자/옵션을 타입으로 고정해 실행 계약을 명확히 하고 테스트 시나리오를 쉽게 만들기 위해서입니다.

3) 검색 함수를 순수 함수로 유지하면 무엇이 좋아지나요?
- 정답: I/O와 분리되어 재사용과 단위 테스트가 쉬워지고 버그 추적이 빨라집니다.

## 학습 완료 기준

1. `main`/`run` 분리 구조로 CLI를 구성한다.
2. 검색 로직을 순수 함수로 테스트 가능하게 유지한다.
3. 옵션(대소문자 무시 등)을 Config로 통합한다.

## 실전 확장 미션

1. 라인 번호/컬러 하이라이트 추가
2. 대용량 파일용 BufRead 스트리밍 버전 구현

## 부가 설명: 프로젝트 장에서 진짜로 배워야 하는 것

이 장은 grep 기능 구현보다 구조 분리가 핵심입니다. `main`과 `run`을 나누는 이유를 이해하면,
앞으로 만드는 모든 CLI/서버 프로젝트에서 같은 구조를 재사용할 수 있습니다.

또한 검색 함수를 순수 함수로 유지하면 테스트와 리팩터링 속도가 크게 올라갑니다.
I/O를 경계에 몰아두는 습관이 장기적으로 가장 큰 생산성 차이를 만듭니다.

## 아주 사소한 것까지: 용어 미니 사전

1. Config: 실행 인자/옵션을 담는 설정 타입입니다.
2. run 함수: 핵심 비즈니스 로직 실행 경계입니다.
3. pure function: I/O 없이 입력->출력만 다루는 함수입니다.
4. case-insensitive search: 대소문자 무시 검색입니다.
5. CLI: 커맨드라인 인터페이스 프로그램입니다.

## 10분 완독 보강: 심화 확장 본문

### 1) 실무 시나리오로 다시 보는 프로젝트 구조화

이 장을 실무에 가져가면 가장 먼저 부딪히는 문제는 "예제에서는 단순했는데 실제 요구사항에서는 경우의 수가 훨씬 많다"는 점입니다.
그래서 개념을 외우는 방식보다, 입력 경계와 상태 전이를 먼저 표로 정리한 뒤 코드를 작성하는 방식이 훨씬 효과적입니다.
특히 변경 요청이 들어왔을 때 어떤 부분이 안전하게 확장 가능한지 확인하려면, 지금 장에서 다룬 핵심 개념을 모듈 경계와 함수 시그니처에 명시적으로 남겨 두어야 합니다.

### 2) 설계 트레이드오프: 순수 함수 분리를 어디까지 강하게 가져갈 것인가

초보 단계에서는 "정답 패턴"을 그대로 쓰는 것이 좋지만, 중급 이후에는 항상 트레이드오프를 함께 봐야 합니다.
검증을 강하게 할수록 안전성은 올라가지만 코드량과 초기 진입 비용이 늘 수 있고, 반대로 빠른 구현을 택하면 단기 속도는 올라가지만 나중 수정 비용이 커집니다.
이 장에서는 안전성/가독성/성능 중 무엇이 현재 맥락에서 우선인지 먼저 정하고, 그 기준에 맞게 구현 강도를 선택하는 훈련이 중요합니다.

### 3) 디버깅 관점: 설정 모델링에서 자주 생기는 실패 패턴

실패는 보통 "핵심 로직"이 아니라 경계에서 발생합니다. 입력 정규화 누락, 상태 전이 누락, 예외 경로 미처리, 로그 문맥 부족이 대표적입니다.
디버깅 속도를 높이려면 함수 단위로 사전조건/사후조건을 짧게라도 적어 두고, 실패 시 어떤 신호를 남길지(에러 타입/로그 키)를 미리 정해 두는 것이 좋습니다.
또한 동일한 문제를 반복하지 않기 위해, 이번 장에서 나온 오답 패턴을 개인 체크리스트로 변환해 다음 구현 전에 빠르게 점검하는 습관을 추천합니다.

### 4) 고급 숙련자 관점: 기능 확장 안전성를 팀 규칙으로 고정하기

개인 실력은 반복으로 올라가지만, 팀 생산성은 규칙으로 올라갑니다.
이 장의 핵심 개념을 팀 규칙으로 만들려면 "코드 리뷰에서 무엇을 반드시 확인할지"를 명문화해야 합니다.
예를 들어 경계 입력 검증, 실패 모델 분리, 모듈 의존 방향, 테스트 최소 세트 같은 항목을 PR 체크리스트에 넣으면 품질 편차가 크게 줄어듭니다.
결국 고급 숙련자는 혼자 잘 짜는 사람을 넘어, 팀 전체가 같은 품질 기준으로 개발하도록 구조를 만드는 사람입니다.
